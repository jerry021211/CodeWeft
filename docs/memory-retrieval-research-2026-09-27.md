**长期记忆检索：第一轮研究与实施边界**

研究日期：2026-09-27。基于 `main` / `a99a514f2d89a8066272b70f5546edd4023bc890` 的当前工作区；原有上下文相关修改保持原样。本轮新增研究脚本和本文，没有改动产品记忆策略，也没有调用真实模型。测量使用合成记忆，不读取用户真实记忆或会话。

结论：第一项优化应是“根据当前任务从完整记忆库生成候选，并记录选择与注入轨迹”。与此同时，要明确中文和代码符号如何分词，以及最新请求如何进入查询。增量索引作为独立性能实验；embedding、自动遗忘和新的记忆生成策略留到有证据需要时再研究。

**1. 先理解当前链路**

```text
新用户请求
  → Agent 把请求追加到 messages
  → MemoryManager.select_context
  → MemoryStore 读取全部 Markdown 正文，按 type/name 排序
  → 截取前 50 条
  → 选择模型读取近期消息预览 + 候选文件名/标题/类型/描述
  → 返回最多 5 个候选文件名
  → 校验文件名属于候选集合
  → 读取正文，按字符预算放入完整记录
  → 选中记忆与本轮用户请求一起进入模型历史
```

关键文件：

| 文件 | 当前职责 | 第一轮需要关注的地方 |
|---|---|---|
| [agent.py](../codeagent/agent.py) | 新用户回合选择记忆、注入历史、统计旁路调用 | `run`、`_selected_memory_context` |
| [manager.py](../codeagent/memory/manager.py) | 候选截取、LLM 选择、预算注入 | `select_context`、`_memory_selection_prompt`、`_recent_message_text`、`_load_selected_context` |
| [store.py](../codeagent/memory/store.py) | Markdown 读写、词频搜索、生成目录 | `_list_memories`、`search`、`_terms`、`rebuild_index` |
| [models.py](../codeagent/memory/models.py) | 配置与记录格式 | 候选上限 50、选择上限 5、注入预算 60,000 字符 |
| [data_paths.py](../codeagent/runtime/data_paths.py) | 按工作区定位运行数据 | 记忆已经按项目隔离；不是待新增功能 |
| [access.py](../codeagent/memory/access.py) | 共享锁、Team 期间写入限制 | 索引缓存不能绕过既有只读约束 |

需要保留的已有行为：每个新用户回合选一次，工具循环中不重复选择；普通子 Agent 写权限单独控制；默认不自动提取；记忆选择已有 `memory_select` 用量分类；超预算保留完整记录，不生成半截 XML。`MEMORY.md` 是给人看的目录，当前搜索并不查询它，所以“已有目录”不等于“已有检索索引”。

**2. 已复现的现象及结论边界**

原始结果：[result.json](../eval-results/20260927T031311Z-memory-research-c0c5fc56/result.json)。目录内保留合成输入、被研究的关键源码副本、SHA-256 清单及 Python/SQLite 版本。脚本使用固定响应客户端，模型调用次数均指脚本化选择器调用，实际供应商调用为零。

| 实验 | 结果 | 能支持的结论 |
|---|---|---|
| 100 / 1,000 条记忆，目标位于末尾 | 候选均为 50 条；目标未入候选 | 自动候选生成受排序位置影响 |
| 固定选择器直接返回末尾目标文件名 | 被候选白名单过滤，未注入 | 后面的模型无法绕过候选遗漏；白名单本身应保留 |
| 仅把候选上限扩大到库大小 | 同一固定选择器返回的目标可以注入 | 正对照确认问题位于候选层；扩大上限不是推荐生产方案 |
| 人工搜索 `NEEDLE_ROUTING` | 命中末尾目标 | 当前手动搜索可检索全集，不能说整个记忆系统找不到它 |
| 搜索“事件” / “事件 回放” | 命中 SSE 约定 | 词面匹配通路可用 |
| 搜索“断线后如何回放事件” | 无匹配；分成一个完整词 | 直接把自然语言请求交给现有 `search` 会漏掉这条中文样例 |
| `exponential backoff` / `RunScheduler` | 命中对应记忆 | 英文词与精确代码符号正对照通过 |
| 中文询问英文记录中的重试等待规则 | 无匹配 | 当前词面方法不能解决这个跨语言改写样例；不是通用语义评测 |
| 关键信息仅在正文中 | 不出现在选择目录中 | 即使召回了记录，选择模型也可能缺少判定证据；未测真实误选率 |
| 2,127 字符请求，尾部有关键标记 | 选择预览不含标记；短请求包含 | 单消息 1,200 字符的头部预览会丢掉尾部；主 Agent 原请求仍完整 |
| 非空库、无关任务 | 仍进行一次选择器调用 | 当前无相关性前置路由；不能断言真实模型一定误注入 |
| 固定选择大、小两条记录，预算 350 字符 | 大条跳过，小条注入 117 字符 | “选中”与“实际注入”必须分别计量；这是预算保护行为 |

性能探针先预热，再测五次：100 条记忆全量列举中位数 28.665ms；1,000 条为 324.792ms；1,000 条手动搜索为 318.056ms。保留原始样本，不以五次测量推断 P95。数据不含 LLM、HTTP 或完整任务耗时，与上轮不同合成记录长度的测量不构成前后优化对比。

这些样例是故障定位材料，不是随机抽样的能力基准。不能把几个固定样例的命中率写成项目整体召回率。

**3. 第一版方案：分清召回、选择、使用**

建议的数据流：

```text
本轮明确请求 + 有界近期意图
  → 中文/英文/代码符号规范化
  → 从完整库做相关性召回，得到候选与匹配片段
  → 现有模型选择，允许选空
  → 候选白名单校验
  → 注入预算与来源标识
  → Agent 完成任务
```

候选只解决“值得让模型看哪些记录”，并不意味着每条候选都应注入。匹配旧规则也不等于旧规则仍然有效。召回分数不应直接被称为置信概率。

建议按以下顺序实施，每一步保留可切换基线，便于定位收益来源：

| 阶段 | 具体变化 | 保持固定 | 交付证据 |
|---|---|---|---|
| S0 观测与基线 | 记录 candidate/selected/injected 集合和跳过原因；形成标注查询集 | 当前排序候选与选择模型 | 每次遗漏可定位到阶段 |
| S1 查询与词法召回 | 显式传入当前请求；合理预算下保护请求尾部；全集召回 | Markdown 存储、现有选择模型、注入预算 | Recall@K、无相关查询表现、查询构建消融 |
| S2 增量索引 | 复用 S1 相同词法特征与排序，减少重复 I/O | 查询、候选数、选择器 | 候选集合一致性、冷启动/热查询/更新耗时 |
| S3 候选证据 | 给选择模型附上命中正文片段和必要来源 | S2 召回策略 | 选择与注入质量，以及额外 Token |
| S4 按需路由 | 研究何时可跳过无收益的选择调用 | 已验证的检索与注入行为 | 少调用是否维持任务质量 |

S1 的初始候选数建议比较 10、20、50；它们是实验参数，不是已经证明最佳的配置。首次先实现全库扫描的词法基线，再做索引，才能区分“找得更准”和“读得更快”。

查询构建应优先使用本轮显式用户请求。短续问如“按上次那个方式继续”还需要有界的近期用户意图或任务信息；不能把全部工具日志无差别加入检索。过长请求可以选取头尾、路径和代码符号，并记录裁剪情况；不直接改主对话历史或上下文压缩策略。显式请求应通过参数传递，避免从已混入历史记忆的消息里反复拼接查询。

第一版仍由模型从候选中选择，不立即用词法分数直接注入。空查询、只有泛化词的查询和简短续问分别处理；现有手动搜索空查询会列出记忆，这是浏览语义，不能直接作为自动检索的“有相关结果”。

**4. 为什么先比较词法检索，暂不确定向量方案**

| 方法 | 本项目适用点 | 必须验证的问题 |
|---|---|---|
| 当前 `search` | 低成本对照，精确词和符号已有通路 | 中文整句分词、长正文词频偏置、全文扫描 |
| 全集 BM25/字段加权词法召回 | 便于解释匹配依据，适合路径、符号、项目术语 | 中文切分、词长与停用词、字段权重及无关候选 |
| SQLite FTS5 | 可作为本地派生索引，不额外部署服务 | 运行环境是否编译支持、分词语义、同步与损坏恢复 |
| embedding 或混合召回 | 值得用于明确的同义改写、跨语言遗漏 | 新模型与更新成本、语义相近但约束相反、项目隔离 |
| 图式记忆 | 可能有助于大量实体关系和多跳事实 | 当前没有实测需求，维护复杂度较高 |

本机 SQLite 3.45.3 的 FTS5 与 trigram 均可用。对“事件断线后应继续回放”：unicode61 查询“事件”“断线后”均不命中；trigram 的“断线后”命中，“事件”仍不命中。默认按连续文字切分不等同中文词语切分，trigram 的三字符窗口也有短词边界。分词、BM25 和片段提取能力可查 [SQLite 官方文档](https://www.sqlite.org/fts5.html)。

可先试中文字符 n-gram 与英文/代码词项组合，再与中文分词方案比较。保留完整标识符并补充分段形式，避免把 `RunScheduler`、`run_scheduler`、文件路径当成普通自然语言。增加近似匹配会带来误召回，需要负例验证；不能依据本轮少量样例宣称一种 tokenizer 已经胜出。

**5. 增量索引的工程边界**

Markdown 继续作为权威存储，索引可删除并重建。索引目录位于项目专属 Runtime 数据目录，包含 schema/tokenizer 版本；不要把用户记忆搬到另一个全局共享库。

文件新增、修改、删除、改名均需要同步。mtime/size 只能作为快速变化提示；同大小修改、时间戳保持、外部编辑都要有明确策略，例如内容摘要校验、定期全量核对和显式重建。目录扫描本身仍可能为 O(N)，不能把“少读正文”宣传为整个刷新过程恒定开销。

原子提交索引代次，查询使用一致视图。模型选择期间文件可能已变化或删除，加载时核对文件版本并记录跳过原因。旧缓存不能覆盖新正文，消失的文件不能继续注入。

Team 期间记忆只读：第一版可以读取有效索引；发现索引失效时在内存回退检索，不擅自写磁盘缓存。跨进程一致性不能仅依赖当前进程内 RLock。讨论模式同样应明确派生索引的写入边界。

**6. 评测应该回答哪些问题**

先做项目自己的有标注查询集，再考虑完整外部基准。建议第一批 60 条查询：每类 6 条，覆盖精确符号/路径、中文自然句、英文改写、跨语言、短续问、正文独有证据、多个相关事实、无相关记忆、带显式新旧依据的约定、文件变更。按主题/事实族划分 40 条开发集与 20 条保留集，避免同一条事实的改写落到两边；不看保留集调权重。最终规模可随人工标注质量调整。

| 层次 | 指标 | 解释 |
|---|---|---|
| 召回 | Recall@10/20/50、首次相关项排名 | 相关记录是否进入候选；无相关题不计算 0/0 |
| 选择 | selected Precision/Recall | 模型是否选对；固定模型和候选呈现预算 |
| 注入 | injected Precision/Recall、预算跳过率 | 选中记录是否真正进入主模型输入 |
| 负例 | 无相关题的误注入率 | 候选非空不等于误注入，必须看最终输入 |
| 时效 | 明确被替代的规则误用率 | 用最终答案/产物判定，不能仅凭检索到旧记录判失败 |
| 工程 | 索引更新一致性、全量构建/热查询/单文件更新耗时、索引体积 | 与召回质量分表展示 |
| 任务 | 约定遵守率、独立验收成功率、模型调用与 Token | 证明组件收益传递到实际任务 |

观测建议每次记录 selection_id、query_strategy、query_hash、是否截断、索引版本、候选 ID/分数/版本、有效选择 ID、注入 ID、跳过原因和各阶段耗时。区分空候选、选择为空、JSON 解析失败、API 失败、文件消失、超预算；现有 Agent 会在选记忆异常时退化为空，用户任务可继续，但诊断不能把所有空结果都当成“没有相关记忆”。默认事件保留 ID/hash/计数，不复制完整记忆正文；隔离评测资产可以保存完整合成输入。

完整任务对照为“无记忆 / 当前策略 / 候选策略”。使用只能从预置记忆得知的合成项目约定，并增加工作区内已有约定和过期约定的对照，防止测成模型常识。先用少量任务验证验收器，再考虑 12 个任务各三次的工程试验。36 次运行不等于 36 个独立任务；逐题配对、保留失败，Token 缺失标未知，费用未核实时不算精确降本比例。

采纳条件应在正式 A/B 前确定：召回与任务收益有证据，保留集上的无关/过期误用不出现不可接受的增加，索引变化用例通过；性能比较使用相同词法策略与相同输入。不能只因为查询更快或 Recall 上升就发布。

**7. 可以借鉴的研究及适用范围**

[LongMemEval 原论文](https://arxiv.org/abs/2410.10813)及[官方仓库](https://github.com/xiaowu0162/LongMemEval)将长期记忆能力拆成信息提取、跨会话推理、时间推理、知识更新与无法回答时的弃答。这里主要借鉴能力分类，特别是新旧约定和无相关信息；本轮没有运行这个基准，也不能把合成诊断结果称为 LongMemEval 成绩。

[LongMemEval-V2 官方仓库](https://github.com/xiaowu0162/LongMemEval-V2)进一步关注工作流程知识、环境中的常见陷阱与前提是否适用，并同时评估答案和查询时延。其 Web/企业轨迹任务与本项目代码任务不同。可以借鉴“测试命令如何运行”“哪些做法在本仓库不适用”的题型，但仍需要自己的代码产物验收。

后续真正引入 embedding 时，再选择固定模型、版本和语料，比较词法、向量、混合方案；不要把一个现成记忆框架的整体成绩归因于某个单独组件。
