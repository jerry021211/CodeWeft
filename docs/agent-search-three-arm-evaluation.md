# 三组真实 Agent 检索对照（2026-10-03）

**已按用户要求将108次缩减为60次，并全部完成。** 主比较采用完整首轮54次（18题×3组），
额外6次重复保留但不混入主表。结论：本轮没有证明整个Agent的成功率或速度提高；
向量组相对词法组的token和热运行费用较低，但差值区间包含零。详见文末实测结果。

证据根目录：`eval-results/agent-three-arm-20261003`。
本实验按用户要求比较**没有 search_code、词法 search_code、向量融合 search_code**，
不将上一轮文本窗口检索消融冒充无检索基线。任务、预算、排列、标签和源码在模型运行前冻结。

## 实验设计

| 组别 | 共有能力 | 本组检索能力 |
| --- | --- | --- |
| A | read_file、glob、grep；修复题另有 edit_file、run_checks | 无 search_code |
| B | 同A | 多语言语法实体、精确符号、BM25、正常模型查询改写 |
| C | 同B | 再加真实 qwen3.7-text-embedding-flash 向量融合 |

三组使用同一个已配置的 DeepSeek Flash、相同系统提示词、默认思考模式和预算。
不强制调用 search_code，允许 Agent 自行决定检索步骤。各组都不接入LSP，防止把诊断收益混进检索差异。
沿用 Agent 自身的通用上下文/待办工具；三组工具schema差异仅为 search_code，修复/只读权限按题型一致。
不开放 shell 或子Agent；这是一组受控工具配置，不能外推为任意工具配置的生产成功率。

每次最多8次真实模型请求（包括改写）、24次工具调用、80000累计token、120秒；单次输出最多3000token。
每组18题各重复2次，合计108次执行。全局向量预算700个HTTP请求、400万输入字符。
任务顺序固定种子20261004，ABC等六种排列平衡；每组在第1/2/3运行位置各出现12次。
每次使用新Agent、新会话，重置**评测专属副本**，不改原项目或用户未提交文件。

为了避免工作区同时发生的提示词修改污染对照，实际执行使用 `execution-engine` 内的冻结生产代码。
`engine-isolation.json`记录检测到的并发变化；没有覆盖这些变化。
`manifest.json`、`manifest-seal.json`保存任务和源码哈希，`execution-protocol.json`保存评分补充说明。

修复题在开始前注入确定性逻辑变异，没有伪造模型的第一步工具调用。
六题都先确认：原源码通过全部隐藏契约，变异版在具体行为断言上失败。
公开检查可供Agent运行，隐藏检查位于工作区之外，任务完成后由外部验证器执行。

Python验证实际Click模块；Java编译实际领域类，但外部注解、Spring辅助类和Pet依赖使用最小stub，
**不代表Spring集成测试通过**；TypeScript通过实际转译后的模块运行行为断言，**不是完整项目类型检查**。
这些限制三组一致。修复成功还要求实际改动且未修改指定目标以外的文件。

证据题要求最终JSON、路径/行号/逐字源码正确，并且五条以内的证据覆盖**所有**冻结关键行；
不只要求找到正确函数，也不使用LLM自评。此标准衡量证据交付，并非对所有自然语言解释进行语义评审。
无答案题要求 `not_found` 和空证据列表；原始工具轨迹留存供检查是否实际进行了查找。

## 量化口径

1. **成功率**：所有执行都在分母内；失败、超时、预算用尽不剔除。分开列证据题、修复题、无答案题。
2. **平均执行时间**：从Agent.run开始到返回/失败，包括模型、读文件、搜索、修改及Agent主动运行公开检查。
   外部隐藏验收时间单列，索引准备时间单列；另外报告含每次索引维护的时间。
3. **token花销**：累计未缓存输入、缓存输入、缓存创建、输出，包含查询改写和重试。
   总token是上述互斥字段之和；缓存命中不代表token没有被处理。
4. **聊天费用**：统一按用户指定的DeepSeek Flash闲时标准价换算，不把账户余额扣费当作估算结果。
5. **向量费用**：分为冷构建、每次索引维护、任务内查询/更新；与聊天费用分列，再给总费用及摊销。
6. **每个成功任务成本**：该组所有尝试总费用÷成功数，失败尝试照样计费。
7. **配对比较**：按任务聚合两次重复，报告成功率、执行时间、token和费用差值及任务聚类bootstrap区间。
   独立任务只有18个、项目只有3个，不能把108次执行当成108个独立样本。

价格核实于2026-10-03，单位为人民币/百万token：

| 项目 | 单价 |
| --- | ---: |
| Flash 未缓存输入 | 1.00 |
| Flash 缓存输入 | 0.02 |
| Flash 输出 | 4.00 |
| Qwen北京区同步embedding输入 | 0.50 |
| Qwen Flash北京区同步embedding输入（本轮C组实际使用） | 0.125 |

公式：`聊天费 = (未缓存输入 + 缓存创建) × 1 / 1e6 + 缓存输入 × 0.02 / 1e6 + 输出 × 4 / 1e6`。
来源：[DeepSeek官方定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、
[阿里云同步embedding](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)。
旧 `deepseek-v4-flash` 别名按官方Flash价格计费；保存每个实际响应的model字段。
服务端聊天缓存无法由本实验强制清空，所以平衡顺序并披露实际命中占比，不声称三组命中状态完全相同。

## 预检及环境事件

- 初版Java验证器没有创建javac输出目录，帮助摘要测试的反排版标记也不符合原函数契约。
  在任何Agent付费对照运行前修正，保留 `preflight-attempt-1.json`；之后六题全部满足原版通过/变异失败。
- 冷建阶段发生两次手动执行中断，均由真实embedding超时导致。其间有19个HTTP子批次成功，服务并非完全不可用。
  32文本构建批次会拆成20+12两个HTTP请求，共用生产实现的10秒截止时间；较高网络延迟可使后半批超时。
- 预建改为在固定预算内续建：每项目最多10次尝试、每任务准备最多3次。没有改生产检索实现、模型、排序或请求超时。
  所有已成功及失败HTTP请求保留。前两次中断没有完整外层wall-time记录，只有HTTP耗时，
  因此不将后续续建耗时宣称为完整默认冷启动性能；冷建token和费用按保留的ledger汇总。
- 评测期间主工作区提示词发生外部修改，改用开始时的冻结引擎，三组都使用同一份副本。
- 续建仍出现累计18次超时后，准备阶段改为使用现有 `max_chunks=20` 参数分片，
  每片只需一个HTTP请求，未修改实际Agent调用的生产检索实现。该措施只用于索引准备。
- 第242次向量HTTP请求返回403，用户确认原模型额度耗尽，并指定换用
  `qwen3.7-text-embedding-flash`。此时尚无Agent对照样本完成。
  Flash真实探测返回200、1024维。全部C组任务统一使用Flash及独立的 `C-flash` 缓存，
  原模型索引、费用和此前102题检索结果全部保留，不重跑已完成评测。
  `embedding-model-amendment.json`记录切换点、价格及原因；原模型未完成冷建费用单列，
  不计入Flash正常冷建摊销，但计入本轮总已知花费。两种模型结果不合并宣称为同一配置。
- 第9条（J1-C-1）Agent执行完成后，评测事件日志并发写入产生残片，导致统计中断。
  原日志保存在 `events.original.jsonl`，完整模型请求/响应未受损。
  从真实响应恢复成绩，耗时使用 `agent.started` 到 `agent.completed` 时间戳（10.157849秒），
  没有重跑该任务；缺少两条事件，事件轨迹完整性存在局部缺口。后续日志写入增加锁，
  100条并发写入检查通过，并在统计前新增结果检查点。详情见 `trace-recovery.json`。
- 前几条结果发现原有JSON解析器拒绝“解释文字+JSON代码块”的回答。
  不修改冻结主分数；另外对全部原回答进行只读JSON提取，沿用相同源码/行号/关键行验收。
  这是观察结果后增加的辅助分析，明确与预注册主指标区分；不修正任何模型证据或重跑任务。

## 复现与证据

```powershell
# 离线预检，不调用聊天/embedding
python -m evals.code_retrieval.challenge preflight --base <新评测目录>

# 真实执行：应在与manifest一致的冻结引擎目录运行
python -m evals.code_retrieval.challenge run --base <评测目录的绝对路径>

# 只重算已保存证据，不访问API
python -m evals.code_retrieval.challenge report --base <评测目录的绝对路径>
```

准备新一轮时先 `prepare --base <新目录> --prior <上一轮公开/仓库冻结数据目录>`。
不要覆盖已有结果。`run`允许从完整记录的已结束trial继续，但不会重跑已失败任务来挑选好结果。
每个trial保存工具schema、模型请求/响应（脱敏、不存思考内容）、事件、最终答案、修改diff及外部验证结果。
`embedding-ledger.jsonl`不保存密钥或源代码请求体；原始任务和源码副本本身仍是本机数据。

费用差[-0.003084, +0.000732]元，耗时差[-1.218, +1.367]秒，全部包含零。
这只能算本批样本的描述性结果，没有证明稳定提升。
相对A，C的热运行费用几乎相同，耗时反而更长；加上索引维护或冷建摊销后，不能宣称更快、更便宜。

主比较没有强制Agent调用检索：B只有6题、C只有7题真正使用了工具。
C的7次完成检索均为hybrid且向量完整，无查询降级或扫描不完整；B有7次完成的词法查询，另一次未完成。
这表明“工具可用”尚未转化为稳定的工具选择行为，不能把全部任务差异都归因于检索算法。
J1-C-1的两个缺失事件会影响事件级工具计数，但完整模型响应与检索完成事件保留。

## 缩减执行、费用与证据

用户提出减量时已完成59次。最初误解为立即停止，当前T6-B-2的一次请求尚无响应；
澄清后只完成这一项，使总量达到60次，剩余48次跳过。
中断请求的原始记录保留在 `interrupted-attempts`，没有重跑任何已经完成的任务。
最终每组20次，其中只有T3、T6有第二次重复，因此主比较使用首轮18题而不让这两题得到额外权重。
补充的6次在 `report.json` 与 `analysis.json` 中保留；全部60次辅助验收为A19/20、B17/20、C18/20。

本轮**已知用量按标准价折算总计约1.03946元**，包括已完成60次、Flash冷建0.049176元、
原模型额度耗尽前的建库0.214340元及探测请求。
23次embedding失败请求与1次用户中断的聊天请求没有用量回执，不能视为免费；
所以这里是已知费用小计，并非完整账户账单，也未将赠送额度折算成零费用。
不包含此前102题评测的费用。后续没有再执行额外真实测试。

9项针对性离线测试通过；评测日志写入修复另通过100条并发写入完整性检查。
六个修复验证器均已预检原版通过、变异版行为失败。生产引擎哈希校验通过，
此前53个结果/报告文件的哈希也全部保持不变。未清理、回退或覆盖用户生产工作区。
