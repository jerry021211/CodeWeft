# Plan Mode

普通 Agent 默认保持执行模式；点击输入框下方的“先出方案”才进入规划。
新建 Agent Team 自动进入规划，后端也执行这一规则。继续已有运行中的 Team
不会重新要求规划。历史 Team 的原有规划记录仍然可用。

## 使用流程

1. Agent 调查项目，用 `plan` 保存 Markdown 草稿。草稿和模式保存在本地数据库，刷新页面仍可恢复。
2. 单 Agent 用 `plan(action="submit")` 提交；Team 用 `TeamPlanSubmit` 同时提交方案与任务依赖、范围和验证命令。
3. 在“查看方案”中阅读全文、切换历史版本、复制或下载 Markdown。
4. “修改方案”返回规划；“放弃方案”退出规划；“批准并执行”启动所批准版本。Team 不再出现第二次相同审批。
5. 启动失败时显示原因并保留方案，可以重试或撤回重做。反复点击批准、服务重启恢复都复用同一次启动记录。

取消当前生成会停止运行，已保存的方案不会丢失；取消运行与放弃方案是两个动作。
只读会话可以生成方案，但批准方案不能解除只读保护。需要先退出规划并更改执行方式，再提交方案。

## 权限与缓存

Plan Mode 使用一套明确的调查工具：项目读取、搜索、`inspect_project` 环境检查和
`project_diff` 差异查看。任意 Shell、源码写入、未知外部工具和可写子 Agent 均被拦截。
Team 可以维护待执行任务，但不能在规划阶段领取或完成任务。
限制同时施加在工具目录、调用入口与 Agent 执行检查，模型无法自行批准或退出规划。

普通执行模式不增加规划工具或提示词。规划提醒追加在上下文中，方案正文不反复改写
系统提示词和工具定义。修改草稿保持系统提示词与工具前缀稳定；进入/退出模式会改变
工具集合，可能使这一次请求重新建立缓存。真实供应商的缓存命中率仍需线上观测。

## 数据和执行边界

`planning_sessions` 保存会话模式；`planning_revisions` 保存不可变的已提交版本、
内容哈希、任务快照、启动状态和执行关联。审批请求必须携带当前版本的内容哈希。
批准前检查调查文件快照及 Team 任务快照；Team 启动事务再次检查任务，防止准备 Git
期间的任务修改绕过用户审阅。文件检查覆盖当前上下文中记录的读取路径（最多 200 个），
不是整个文件系统的锁或完整快照，也不覆盖外部资料、子 Agent 调查的全部内容。

规划期间不创建 Git 快照、Worktree 或运行 Team Worker，所以空目录和非 Git 项目
也可以生成方案。批准新 Team 方案后，Runtime 会为非 Git 目录初始化本地仓库，
为尚无提交的仓库创建一个空的初始提交；用户文件和暂存区保持原样，再由临时索引
捕获本地内容供 Team 使用。不设置远程、不推送、不要求全局配置 Git 用户名。
已有正常 HEAD 的仓库直接复用；中断后重试不会重复创建初始提交。
Git 未安装、仓库损坏或工作目录不是仓库根目录时仍会提示原因。已有本地快照、集成和交付流程继续复用。

## 验证

```powershell
python -m unittest tests.test_plan_mode tests.test_web_scheduler tests.test_web_api tests.test_team_api tests.test_team_lead
cd web
npm.cmd test
npm.cmd run build
```

测试覆盖版本冻结、旧版本拒绝、只读保护、空目录规划、单次启动、Team 审批、
启动恢复、源码/任务变化、工具权限和提示词前缀稳定性。浏览器交互使用隔离数据库
和模拟 Agent 验证；不代表真实模型已经完成 SeatFlow 项目的端到端开发。
