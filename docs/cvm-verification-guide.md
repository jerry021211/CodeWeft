# 验证监督：开启与调试

这一版落实新方案的第一步。作用是：Agent 改过代码后，程序记住指定测试检查过哪个版本；后来文件又变了，界面显示旧结果过期。在下一次正常的模型请求里，可以发一条具体建议。它不会自己调用命令，也不会因为没测试而强制模型继续。

## 开启

默认关闭，保留原来的运行方式。普通单 Agent 模式下，在启动后端的 PowerShell 中设置：

```powershell
$env:CODEAGENT_CVM_CONTRACT = 'shadow'
$env:CODEAGENT_CVM_EVIDENCE = 'shadow'
$env:CODEAGENT_CVM_VERIFICATION = 'active'
```

然后从这个终端按原来的方法启动后端。也可以把对应的三个键值写入自己的 `.env` 后重启。这次修改没有改写你的 `.env`。

- `verification=active`：显示状态，并在条件满足时发送建议。
- `verification=shadow`：显示状态、记录候选建议，不把新建议放进模型请求。用于之后做对照。
- `verification=off`：关闭这个新功能；其他已有 CVM 开关保持各自配置。

`contract=shadow` 只是保留任务身份，不会启用旧目标的主动提示。新开关依赖 `evidence=shadow`。Team 继续关闭 CVM；子 Agent 不替父 Agent 发送建议。

每个受支持的工作区配置一次 `.codeagent/cvm-verification.json`。本仓库提供了 [配置示例](examples/cvm-verification.json)，可在项目根目录执行：

```powershell
New-Item -ItemType Directory -Force .codeagent | Out-Null
Copy-Item docs/examples/cvm-verification.json .codeagent/cvm-verification.json
```

已有同名文件时先合并自己的配置，不要直接覆盖。`.codeagent` 本来就是本地忽略目录，团队共用配置时请另行保留可追踪的示例。

示例检查的是此次监督功能的 Python 测试，不是整个项目的全部测试。配置中的 `command` 是准确匹配的检查命令，`cwd` 相对工作区，`inputs` 相对该工作目录、列出会影响结果的源码、测试和配置文件。支持明确的文件或目录，不支持通配输入、越界路径、shell 拼接和自定义脚本。当前只认识简单的 unittest/pytest 命令；npm、构建和类型检查尚未接入。

配置仅描述范围，绝不自动执行命令或授予权限。每次真实用户输入时重新读取；运行中修改配置会显示未知，原通过记录失效。配置自身也算作检查输入。没有可靠配置就显示未知，不猜测整个项目已通过。

## 在哪里看

Web 右侧 **运行 → 验证状态** 显示每项检查的状态、命令、目录、输入范围和结果引用。打开同一个运行的 **调试 → 原始事件** 查看：

| 事件 | 看什么 |
| --- | --- |
| `cvm.verification_status` | 每项检查是通过、失败、过期、受阻、尚无记录还是未知 |
| `cvm.verification_advice` / `phase=candidate` | 规则为什么产生建议；不表示模型已经收到 |
| 同事件 / `phase=delivered` | 完整建议包含在最终模型客户端请求中，且调用返回了响应 |
| 同事件 / `phase=followup` | 提醒之后有没有尝试对应检查、是否完成、是否通过、当时是否对应当前文件 |

`delivered` 不代表模型理解或采纳。调用失败或取消时，即使请求可能已到服务器，也不会冒充确认送达。后续检查发生在提醒之后，也不等于已经证明“是提醒导致模型做了检查”。

数据库不增加新表。上述事件仍在 `events`；原始证据和本次提醒去重状态仍由既有 checkpoint 持久化，CVM 包里的 `evidence` 保存检查原始记录，`supervision` 保存任务起点、等待机会和已送达事实。Web 根 Agent 的状态随现有会话 checkpoint 保存。建议优先看界面，避免直接编辑数据库。

## 如何演示

1. 开启并配置一个小 Python 项目，向 Agent 明确提出修改和检查要求。
2. 指定检查通过后，让它再改相关 `.py` 文件：下一次请求前或结束前应显示“旧结果已过期”。
3. 程序给正常的“编辑后测试”留出一批工具执行机会。若它继续做别的事、没有新验证，再有模型请求时，会收到一次建议；如果直接结束，只留下状态，不增加请求。
4. 再跑同一项检查，通过后状态回到“指定检查通过”。无关检查通过不会清掉该项失败。

不想依赖真实模型时，从仓库根目录运行完整可重复的演示测试：

```powershell
python -m unittest discover -s tests -p test_cvm_supervision.py -v
```

其中 `test_real_pass_edit_stale_once_recheck_current` 用固定模型响应、真实文件和真实 Bash/unittest 完成“通过 → 修改 → 过期 → 提醒一次 → 再检查通过”，同时断言没有新增模型轮次。

## 边界

当前只在明确发生了 Python 文件变化时提示缺少验证；已识别、尚未被同项成功检查替代的失败也可产生建议。同一任务、代码版本和检查事实只确认投递一次，恢复会话不会重置这个记录。缺少测试但没有代码变化、纯文档编辑、只读和规划模式保持安静；常见的禁止检查或暂停指令会抑制建议，待确认的自然语言任务修订也只展示事实。禁令在同一任务内保守保留，开启新任务才重置；这不是完整的自然语言授权识别器。

文件范围在模型请求和结束等判断边界核对，不在每个 token 中扫描。启动前已有的修改属于起始版本。没有范围、未知命令、零测试、全部跳过、输出残缺、取消、超时和未完成进程，都不能证明当前检查通过。

第一步的这些测试证明接线与边界行为，不证明真实模型收益。后续第二步已补充真实模型对照设施，运行与读报告方法见 [CVM 对照评测](cvm-evaluation-guide.md)；收益结论应以实际批次记录为准。
