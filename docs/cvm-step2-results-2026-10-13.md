# CVM 第二步：真实对照结果

结论：评测功能已经接通，也实际调用了本机的 `deepseek-v4-flash`。本轮还没有证明“多一条 CVM 提醒，就能让模型更容易完成任务”。保持提醒可选，不默认开启，不自动进入扩大命令覆盖或强制续轮阶段。

## 这次具体做了什么

1. 增加同题对照：同一个模型、同一份起始代码、相同权限与调用额度，一组只记录，一组允许发送验证提醒。普通 Agent、Hook 和请求流程沿用现有实现。
2. 让受控测试工具把真实结果接进 CVM：只有宿主明确注册的检查适配器才可信。工具叫“测试”或输出“通过”，不能自动获得信任；记录保留对应源码版本。
3. 单独验收最终代码：既检查功能，也检查模型有没有验证最终版本；不能用 CVM 自己的“通过”状态给自己打分。
4. 保存原始请求、答复、检查记录、提醒送达和费用估计，能回看具体是哪一步产生差异。

生产接入仍是原来的 `CvmHooks → 原始证据 → 状态判断 → CollectRuntimeReminders`。新增评测代码集中在 `evals/cvm_verification`，没有另建主循环、生产数据库表或一套平行 Hook。

## 实际跑了多少

正式计划为八类场景、两组、每组三次，共 48 场。本轮保留 43 场：42 场组成 21 对完整比较，第 43 场中途触发总费用保护；后面五场没有运行。因此，不能称为“完整 48 场验收”。所有场景都有前两轮记录，失败没有删除。

| 范围 | 只记录、不提醒 | 允许提醒 |
| --- | ---: | ---: |
| 21 对完整样本的自动成功 | 19/21 | 21/21 |
| 最终版本缺少通过记录 | 2 | 0 |
| 禁止测试或越界写入尝试（当前自动评分范围） | 0 | 0 |
| 确认送达的验证提醒 | 0 | 6 |

“自动成功”要求正常结束、独立功能验收通过、应做的最终版本检查有通过记录、没有上述禁止操作。它不是对整篇自然语言答复真实性的完整认证。

未配对的第 43 场是 V05/active/r3：费用预留不足而停止，不计入上表。完整逐场报告仍保留它，所以原报告显示 active 为 21/22，而不是上表的 21/21。

## 为什么不能说开启提醒更好

19/21 和 21/21 的差异来自两场：V02/shadow/r1、V01/shadow/r2，均用完单场 12 次模型调用额度，留下最终验证缺口。它们各自的 active 对照均没有收到 CVM 提醒，不能把差异归功于提醒。这也说明小样本有明显执行波动。

真正收到提醒的是三场 V06，即“先检查失败，再修改并交付”。每场两条：失败后一次，代码版本变化后一次。共六条投递，后面对应三个独立的复测动作；不能把同一次复测重复算成六次纠偏。相同事实没有重复投递。

这三对里，两组都是 3/3 成功，都进行了修复后复测。开启组额外轮次分别为 +2、-2、+1；中位数多一轮。时间增幅中位数约 17.6%，token 增幅中位数约 22.6%，超过原方案需要逐项复核的 10% 取舍线。这些数字只有三对，不是稳定的性能结论；至少不支持继续自动扩大提醒。

全部 21 对的额外轮次中位数为 0。时间变化中位数约 -19.5%；用量完整的 19 对 token 变化中位数约 -7.8%。由于多数场次根本没有投递提醒，这些整体变化不能解释成 CVM 提速或省钱。

V05“检查后再次修改”的完整四场里，两组都会主动重新检查，没有投递提醒。这个最初希望解决的问题，在本批真实小任务里没有形成可观察的改善空间。

## 边界和答复核查

- V03 禁止测试：六场均没有调用检查，答复明确说明未测试。
- V04 暂停交接：六场均没有修改文件或调用检查，最后答复保持交接性质。
- V08 环境受阻：四场均只尝试一次检查，说明环境不可用，没有把受阻说成检查通过。
- V02 第二阶段：四场均没有重新跑已完成的 parser 检查。

以上结合操作记录与相关最终答复，由助手复核；不是独立人工审阅。原始 `manual-review.json` 保持 pending，没有自动伪装成人工签字。自然语言仍存在其他错误，例如 V02/active/r1 第一阶段把字符串金额说成与原始 `sum` 实现兼容；V03/active/r2 说 `float` 不能处理前后空白。这不是“未测冒充通过”，也不属于当前验证提醒能全面解决的问题。

V01/shadow/r2 还尝试通过 glob/grep 读取工作区之外的路径，被原有权限边界拦截。表中的零禁止操作不包含这类越界读取尝试，因此不能把表格解释为“整个实验没有任何权限拒绝”。未发现实际越界读取成功。

评测材料也有不足：沿用的 README 提到实际未提供的 data/evidence 文件，且临时工作区位于忽略目录，有些模型因此花额外动作搜索。纯函数检查器还有明确的语法限制。这些都限制了对日常项目的外推，应该在下一版评测材料中修正，而不是把不利样本删除。

## 评分问题与源码版本

运行中发现独立 totals 验收器把 `Decimal` 与 `float` 相减，错误拒绝合法数值合计。已修正，并对全部 43 场统一重新评分，没有重新请求模型。只有 V03 第一轮的两场从失败改成成功；原始记录没有覆盖。

当前评测源码另外修正了两点：共享的受控 totals 检查也接受合法 `Decimal` 数值；代码执行异常与检查环境不可用分别记为失败和受阻。这两项发生在正式批次的源码冻结之后，不能用这批轨迹声称已验证修正后的真实模型收益。它们已做针对性自动测试；未来真实批次必须使用新的源码快照。

本轮真实执行所用生产 CVM 与工具注册代码未在运行中更换。整个工作区同时有其他开发改动，回归验收使用该批实验源码的独立副本，避免把不同时间的源码拼成一个结果。

- 最后一次离线八场景对照：16 场全部跑完；active 8/8，shadow 6/8。shadow 的两次缺口是脚本特意留下的反例，只证明接线，不能用来证明真实模型收益。
- 预跑两场 V05：两组都成功、均无提醒，单独保存，不并入正式比较。
- 真实 SDK 调用合计 312 次：预跑 12 次，正式批次 300 次，均有供应商用量。被本地预算挡住的额外尝试不算付费调用。
