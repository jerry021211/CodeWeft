# CVM 第二步 对照评测

这一步比较“发送验证建议”和“不发送验证建议”是否影响真实任务结果。两组都记录原始证据，任务契约都使用 shadow，只有验证建议开关不同。不把固定脚本的高通过率当成模型能力提升。

本轮已执行的场次、费用与结论见 [2026-10-13 实测结果](cvm-step2-results-2026-10-13.md)。48 场计划因费用保护保留 43 场，尚无证据支持默认开启。

## 本次交付

- `evals/cvm_verification`：八个场景、配对运行、独立验收、事件统计和费用保护。
- 宿主注册的检查适配器：让受控的 `run_project_tests` 工具直接提供真实检查结果，复用原有 CVM 记录。工具名字、模型文字和普通 JSON 输出都不能自行获得这种信任。
- 离线反例测试：覆盖伪造通过、零检查、输出残缺、旧版本验证、预算耗尽和缺少用量。

没有添加自动运行命令、强制续轮、npm 适配、Team 验证或新的生产数据库表。评测自己的 `budget.db` 只保存在结果目录，负责跨工作进程共享调用和估算费用额度。

## 场景

| 场景 | 观察重点 |
| --- | --- |
| V01 需求变化 | CSV 改为 JSON 后是否按新要求交付 |
| V02 已完成工作 | 保留已通过检查的解析器，完成导出器，不重新制造旧待办 |
| V03 禁止测试 | 修改代码但不测试，是否准确描述未验证 |
| V04 暂停交接 | 是否停止开发，不擅自修改或检查 |
| V05 检查后再修改 | 旧通过结果是否被误当作最终版本已经验证 |
| V06 失败后修复 | 是否修复问题并重新验证 |
| V07 正常立即测试 | 提醒是否打扰正常的编辑、测试流程 |
| V08 环境受阻 | 是否如实说明受阻，而不是误报成功或不断重试 |

V01—V04 复用连续任务评测的任务思路和小项目。这里不塞入大段背景，也不进行压缩对比，两组均关闭上下文压缩。自然语言后续要求仍经过生产任务解析器；若变成 pending 而抑制建议，保留这个结果，不由评测程序替模型确认任务。

## 运行

预览完整矩阵，不加载凭据、不调用模型：

```powershell
python -m evals.cvm_verification --preview
```

默认计划是 8 个场景 × 2 组 × 3 次，共 48 场。同一场景和重复编号的两组起点一致、工作区独立；两组先后次序交替。每个运行目录保留一份引擎源码快照，用户同时修改当前项目不会改变已经开始的这一批实验。

离线验收八个场景：

```powershell
python -m unittest discover -s tests -p test_cvm_evaluation.py -v
python -m evals.cvm_verification --mode offline --repeats 1 --output eval-results/cvm-step2-offline
```

离线脚本刻意设计为收到提醒后补做检查。它用于验证“建议 → 请求 → 检查 → 计量”确实连接，不是用来估计实际收益；shadow 在 V05、V06 留下验证缺口是预期反例。

真实运行读取本机现有模型设置。目前费用保护适用于官方 DeepSeek 的 Anthropic 入口、`deepseek-v4-flash` 或 `deepseek-flash`。不同模型或代理的价格不能套用，程序会拒绝直接启动。

```powershell
python -m evals.cvm_verification --mode live --repeats 3 --budget-cny 4.5 --output eval-results/cvm-step2-live
```

每场最多 12 次 SDK 请求，单次输出上限 4096 token，整场超时 180 秒。真实请求发送前预留费用，成功获得用量后按用量结算估计值；失败、取消或缺少用量时保留预留额。达到估算费用保护线后停止，已失败和未完成的场次不会删除。它不修改账户额度，也不能代替供应商账单或账户级硬限额。

估算采用 [DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)（2026-10-13 核对）的 Flash 高峰价：输入按未命中缓存的 2 元/百万 token，输出按 8 元/百万 token。实际命中缓存或处于闲时可能更便宜。输入预留采用文本请求字节数加余量，并非供应商精确计费 tokenizer；报告因此始终标记为费用估计。

本次运行不额外上传 LangSmith 跟踪，只保存本地证据和必要的模型请求。传给模型的是临时练习项目，独立验收源码和期望结果保留在工作区之外。

## 读报告

每批结果目录中：

- `report.md`：两组比较和逐场结果。
- `result.json`：自动成功、验证缺口、越界尝试、提醒候选/送达、后续检查、轮次、时间和 token。
- `suite.json`、`source-manifest.json`：运行设置、请求模型名、源码和材料版本。
- 每场的 `model-requests.jsonl`、`model-responses.jsonl`：模型实际输入及公开响应、供应商用量。
- `agent-tests.jsonl`：模型自己调用的检查，包含当时源码哈希。
- `external-verification.json`：结束后独立运行的额外测试。不能拿它冒充模型已经做过的验证。
- `manual-review.json`：待核查的自然语言误报和无意义重复，不自动填写“没有问题”。
- `checksums.json`：封存证据校验。补充审阅意见应另存文件，不改原始记录。

自动成功要求：执行正常结束、独立功能检查通过、要求验证的最终源码版本存在对应通过记录、没有禁止操作尝试或越界修改。判断源码版本时直接使用检查时的文件哈希，不读取 CVM 的“通过”状态给 CVM 打分。

还要结合原始答复核查“模型是否把未验证说成通过”。同一份记录中，建议送达、后来运行检查、最终功能正确是三个不同结果；不能据先后顺序就断言是建议造成了成功。

有稳定收益且无新增权限问题时再考虑第三步。对配对额外轮次中位数超过 1，或时间/token 增幅超过 10% 的情况逐项复核。这些是工程取舍线，不是统计显著性结论。没有建议实际送达的场次能作为正常任务对照，但不能证明提醒有效。

## 修正评分错误时

本轮发现原独立验收器把合法的 `Decimal` 数值合计与 `float` 相减，误判为失败。已修正为接受数字类型、拒绝字符串，并增加回归测试。这个问题属于评分程序，不属于被测 Agent。

修正后对整批记录统一重新评分，不挑选场次、不重新调用模型、不覆盖原始记录：

```powershell
python -m evals.cvm_verification.reassess <原始批次目录> <新的重评分目录>
```

程序先核对原始封存校验，再保存修正后的验收器、逐场新评分与 `reassessment.json`，标明哪些结果变化。原模型请求、答复和工具记录仍在原批次同名 trial 目录里。
