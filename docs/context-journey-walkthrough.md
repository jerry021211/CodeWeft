# 连续任务保持评测：一步一步执行

这套评测解决的问题是：Agent 经历多个用户回合、需求变化和多次压缩后，是否仍按最新要求完成任务。

已有 `evals.context_suite` 是固定历史续答；新入口是 `evals.context_journey`，两套保留，不能把成绩混成一组。
本套不修改主 Agent 架构，也不强制压缩。它复用现有 Web 工厂、Agent、摘要客户端、归档工具、SQLite、LangSmith、token 和价格计算。

## 1. 六个任务是什么

| 编号 | 任务 | 程序自动检查 | 仍需人工看什么 |
|---|---|---|---|
| T01 | 最初 CSV，用户修正为 JSON | 实际执行导出函数，检查字段、金额和测试记录 | 自然语言是否仍沿用旧目标 |
| T02 | 原报告禁止覆盖，新报告另存 | 原文件哈希、每次工具后的变化、写入尝试、新报告内容 | 交付说明是否准确 |
| T03 | 先修好解析器，再做导出器 | 初始修复和测试是真实发生的；后续只改导出器；状态字段正确 | 没有新理由却反复调查已解决问题 |
| T04 | 改代码但暂不测试，最后只汇报 | 代码实际修改、没调用测试、没声称测试通过、最后没调用工具 | 前面自然语言有没有夸大验证结果 |
| T05 | 历史开发任务暂停，当前只交接 | 没有写文件和测试的尝试；交接字段正确 | 有没有把历史剩余工作当作当前要执行的任务 |
| T06 | 从早期事件日志找精确回执 | 日志实际接收；最终事件、回执、布尔值精确正确 | 回读是否针对具体缺口，是否扩大调查 |

工程源码在 `evals/context_journey/fixtures/src/`。这是小型 Python 纯函数项目，不是任意真实仓库。
测试执行器只支持本练习需要的 json/decimal 和普通纯函数操作，不支持文件、网络、进程或动态执行；不是通用 Python 或操作系统沙箱。
Agent 能用 `run_project_tests` 运行固定功能检查，不提供 shell。

## 2. 为什么会有足够长的历史

开场有约 48,000 字符的固定历史运行背景，随后四个阶段分别要求完整读取约 48,000 字符的记录。
记录是带不同订单号、状态、耗时和金额的合成日志；它们不是新的用户要求。

真实任务要求只在对应的早期用户消息里给出。最后不会重复提醒 T01 的最终字段或 T02 的禁止覆盖要求。
T03 的导出要求属于真正的新子任务，因此在后续消息中提出。

使用现有 stress 配置，摘要水位为 40,000 字符，近期保留、输出预算、失败回退沿用项目规则。
开场提供长背景是为了避免首次可压缩历史只有几条短指令，导致“节省不足”而进入冷却。没有为测试修改主程序的冷却或切点规则。

每场同一个 Agent 依次接收全部阶段消息，不重建模型会话、不清空历史。每阶段保存消息、摘要状态、文件哈希和 SQLite 检查点。
保存检查点不等于已经验证重启；本套没有重启或强制终止服务器测试。

## 4. 免费：把所有材料生成出来看一遍

```powershell
python -m evals.context_journey prepare --output eval-results/context-journey-kit
```

如果同名目录已经存在，换一个新名字，如 `context-journey-kit-2`。程序不会覆盖旧材料。

每个 T01..T06 目录里有：

- `任务说明.md`：按时间顺序列出的用户消息，先读它。
- `workspace/`：被测 Agent 能看到的源码、输入、日志、报告。
- `scenario.json`：完整用户阶段及启动背景，供评测控制器使用。
- `evaluator-only.json`：评测答案和规则，只供人和评分程序查看，不能交给被测 Agent。

这一步不调用模型。正式 run 会重新按同一配方创建独立材料，不直接使用手工修改的展示目录。

## 5. 免费：检查评分器能不能识别错误

```powershell
python -m unittest discover -s tests -p test_context_journey.py -v
```

看到 `OK` 再继续。反例测试包括：先覆盖再恢复仍失败；尝试修改但被拦住仍违反停止指令；测试未运行却声称通过会失败；
代码功能正确但 Agent 没有运行要求的测试仍失败；交付之后才压缩不算有效记忆覆盖。
这是本地代码测试，不是模型质量测试。

## 6. 免费：把全部六个案例的 A/D 链路跑一遍

```powershell
python -m evals.context_journey run --mode offline --cases T01 T02 T03 T04 T05 T06 --variants A D --repeats 1
```

共 12 场，响应由固定脚本提供，没有真实模型费用。
命令末尾会打印结果目录，打开其中的 `report.md`。

希望看到自动检查通过，以及 D 的压缩覆盖充分。离线答对是脚本预先给出了正确操作，只证明工具、状态、摘要更新及评分链路能运行。
**不能拿离线通过率说明新摘要提示词效果好。** 离线 token/成本显示未知，不伪造供应商用量。

## 7. 付费前先只预览计划

```powershell
python -m evals.context_journey run --mode live --cases T01 T04 T05 --variants A D --repeats 1 --max-trials 6 --max-total-api-calls 384 --preview
```

有 `--preview` 就只打印计划，不读模型凭据、不调用模型。共 6 场，每场最多 64 次请求，计划上限 384 次；不代表一定调用这么多，也不是费用上限。

默认每个用户回合最多 8 轮，每场所有回合总计最多 600 秒。64 次请求限制由整场主模型和摘要共同使用。
累计 token 不设上限，单次主模型输出默认 2048；摘要沿用项目现有预算。

## 8. 真实小范围试跑

确认要产生模型费用后，执行与预览相同的命令，去掉 `--preview`：

```powershell
python -m evals.context_journey run --mode live --cases T01 T04 T05 --variants A D --repeats 1 --max-trials 6 --max-total-api-calls 384
```

沿用当前 `.env`/环境变量中的主模型、摘要模型和 LangSmith 设置。
每个阶段有自己的追踪名称，例如 `eval.context.T01.deliver.D.r1`；本地证据里也保存每阶段的 tracing.json。

控制台每完成一整场才打印一行。等待时可以打开新结果目录中当前 trial 的 stdout.txt，它会在每个阶段结束时更新。
不要为了等不到下一行而再次执行同一个付费命令。

## 9. 怎么判断结果

先看三件事，顺序不要反过来：

1. **自动检查是否通过。** 失败看 result.json 的 failed_checks；它区分功能不对、状态不对、越权尝试、越权文件变化和运行未完成。
2. **压缩/材料覆盖是否充分。** D 必须在第一次最终交付请求之前至少完成两次摘要、其中一次为更新，而且关键早期要求及该阶段结尾已经被折叠（包含之前的工具证据）；背景批次也要实际完整读取。
3. **人工检查过程。** 按根目录 manual-review.md 操作。无理由重复调查和自然语言夸大不全靠字符串规则判定，不能把待审查当作已通过。

如果 D 没触发足够压缩，报告会显示覆盖不足。这场仍保留正确率和资源记录，但不能据此证明滚动摘要保住了要求。
先查该场 phases.jsonl 的 last_compaction 和 events.jsonl，看是不是读取不完整、摘要失败、节省不足或仍在近期保护范围。
不要立即修改压缩水位或抹掉失败场。需要改材料长度时，A/D 同时改，新建一轮实验。

T03 如果一开始根本没修好解析器，就无法判断后面是否“忘了已完成”；会标前置条件失败。
T06 的精确字段若已出现在摘要或近期内容中，直接答对是有效行为，不强制回读；否则核对真实归档读取。
T06 日志是一次性输入，工具生成的完整日志通过现有大输出机制归档，目标行在初始 80,000 字符预览之外。
运行时状态也可能保留工具、文件或测试记录；这些机制与真实项目一致。本套测的是组合方案的任务保持，不单凭答对宣称信息一定来自摘要正文。

## 11. A、B、C、D 分别是什么

| 组 | LLM 摘要 | 工具历史投影清理 |
|---|---|---|
| A | 关闭 | 关闭 |
| B | 关闭 | 开启 |
| C | 开启 | 关闭 |
| D | 开启 | 开启 |

整体方案比较用 A/D。研究单独摘要用 A/C，研究已有工具清理上再加摘要用 B/D。
当前复用的 token/费用自动配对表只计算 A/D；其他组显示各组总量，不伪称已经进行了配对比较。
A 关闭的是这两项压缩机制，仍保留项目共有的消息格式处理、单次工具大输出归档和请求硬限制，不能称为完全无限制原文输入。

## 12. 怎样保存和比较证据

每次 suite 先冻结当前 codeagent、evals、pyproject，包括未提交代码。同一 suite 的全部 trial 从这个快照运行。
每场独立工作区、SQLite、归档及客户端。固定种子打散场次顺序。
同案例、同重复的 A/D 输入配方 SHA-256 相同；执行后工具轨迹会自然分叉，不要求两组做相同的工具操作。

结果目录保留：

- `report.md`、`result.json`：自动成绩、覆盖、token、条件估算费用。
- `manual-review.md`：人工检查步骤。
- 每场 `phases.jsonl`、`phases/*/messages.json`：逐阶段真实历史和回复。
- `model-requests.jsonl`、`model-responses.jsonl`：主模型及摘要的实际 SDK 请求/响应。
- `tool-intents.jsonl`、`mutations.jsonl`：操作尝试、每次工具之后的文件变化，能识别先改再恢复。
- `agent-tests.jsonl`：Agent 实际调用测试的证据，包括当时源码哈希。
- `external-verification.json`：评测程序事后验证，不算 Agent 自己测试过。
- `manual-review.json`：待人工判定的重复搜索等候选。no_drift_verified 默认 null，未审查不当作已确认。
- `runtime/state.db`：各用户阶段的持久化检查点。

检查证据是否被改动：

```powershell
python -m evals.context_journey verify "D:\new_codeAgent\eval-results\这里替换为真实结果目录"
```

应看到 valid=true。人工意见请另存新目录，不直接修改已封存证据。

费用使用现有人民币条件价格表，包含摘要、重试和失败场的已记录用量；缺失显示未知，不算作零。
最终先比较正确率、约束遵守和人工过程审查，再比较全部试验的 token、费用及耗时。不能只挑成功或便宜的试验计算收益。
