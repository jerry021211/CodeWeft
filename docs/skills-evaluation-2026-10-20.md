## 流程发现

1. 早期试跑曾出现代码修复正确但不加载技能的情况。运行时技能提示现在明确要求：点名或直接匹配专业技能时先加载正文，不把目录描述当作完整流程。没有设置基于关键词强制路由，也没有声称提示修改能保证遵循。
2. 完整运行中，故障修复的隐式、显式两例都观察到加载、读取实现和测试、失败基线、修改、通过验证，独立测试再次通过。只有 `totals.py` 被修改。
3. API 契约案例读取了服务端与客户端，正确指出 `display_name` 的 `None/null` 与 `string` 冲突，但没有调用 `load_skill`。因此任务回答中的事实锚点通过，加载和总体检查失败。
4. 没有把模型“我按流程做了”的自述作为加载或测试证据。

## 人工审阅补充

自动通过不代表回答的全部建议正确。SQLite 案例正确识别了旧表增加无默认值的 `NOT NULL` 列会失败，但回答进一步提出 `NOT NULL UNIQUE`，其中唯一性是任务未要求的业务约束。该项未被事实锚点评分捕获，实际采用迁移方案前仍需检查；这也是后续增加语义 rubric 的具体样本。

目前分析类案例只检查加载、关键文件读取、范围、正常结束和少量事实锚点。没有自动验证回答中的每一条建议，也没有把这些检查称为完整质量验收。不要把 16/17 当作所有技能的生产可靠性结论。

## 评分器修正与原始证据

初次评测器未计入批量读取，且默认提示工作区错误，调试运行被主动终止，不纳入完整成绩。修正后重新执行了完整 17 例。

完整运行的原始自动结果为 15/17；其中缺失文件案例使用绝对路径，评分器错误地按字符串比较相对路径。修正为工作区内等价路径后，用原始工具记录免费重算得到 16/17，没有放宽“实际读取失败并如实报告”的标准。

原始汇总的用量因包装客户端未接入 UsageTracker 而为零，供应商响应的逐次 usage 已完整保存。最终报告据此重新汇总，并修复后续运行的计量；没有将旧零值当作免费调用。评分器增加了批量部分失败、绝对路径缺失、用量缺失以及 SDK 推理字段脱敏的回归覆盖。
