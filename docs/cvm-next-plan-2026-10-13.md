# CodeWeft CVM 后续修改方案

这份方案从当前代码重新出发，替代此前方案的后续排期。已经写好的功能按实际用途复用，不因为已经投入就继续扩大。目标是让 Agent 少漏检查、少把旧检查当成当前结果，同时让用户看得懂程序为什么提醒它。第一步就交付一个能看见行为变化的小功能，再决定是否值得继续。

研究依据是 Tianshu 公开仓库提交 `81924691de67364dddd4beb00829a2217452b072`，版本 `3.30.0`、提交日期 2026-10-12；用户提供的 CVM 讲解；以及当前 CodeWeft 工作区，包括刚完成的 Hook 重构。本文是实施建议，本次没有启用新规则或开展真实模型实验。

**从 Tianshu 借什么**

Tianshu 最值得借鉴的是一个工作过程：程序记录实际操作，把记录整理成当前状态，发现具体遗漏时给模型一条建议，再看它后面有没有处理。少数必须控制的情况，才直接影响工具执行或结束流程。

例如：改了代码，测试通过，随后又改了相关代码。程序应记住“旧测试通过过，但当前版本还没有新验证”，而不是一直显示“通过”。Hook 负责在合适的时机检查和通知；证据、提醒投递和主循环的继续或结束判断共同完成这个过程。

源码依据：[证据状态](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/src/agent/evidence.ts#L137)、[验证提醒规则](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/src/agent/hooks/self-verify-hook.ts#L144)、[统一投递与请求构建](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/src/agent/turn-step-producer.ts#L649)、[有限的结束前补证](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/src/agent/turn-orchestrator.ts#L1524)。

附件的主要解释与这些代码相符，但使用时要守住三个区别：

- “发现问题”“提醒实际送到模型”“模型采取了动作”“任务最终做对”是四件事，必须分别记录和评估。
- 广义 CVM 不等于 CVM-vector。后者默认 shadow，只记录该通路的判断；其他 Hook 仍可以工作，不能把它的计数全当成有效纠偏。
- README 的五题 A/B 实验明确只支持信念提示词这一层的初步效果，不能替整套 CVM 或本项目证明收益。附件所称测试通过数量属于那次研究的执行记录，本次不把它当作重新运行的结果。

对应依据：[CVM-vector 模式](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/src/agent/hooks/cognitive-capsule-router.ts#L645)、[README 实验范围](https://github.com/huiliyi37/Tianshu-harness/blob/81924691de67364dddd4beb00829a2217452b072/README.md#L219)。

**你现在已经有的东西**

| 当前能力 | 后续怎么处理 |
| --- | --- |
| 观察通知、控制判断分开的 Hook 管理器 | 保留，不再建第二套管线 |
| 工具原始结果、重试、取消、并行入账 | 复用，保持原始事实早于后置 Hook 的采集位置 |
| 任务原文、要求、版本和检查点 | 保留；不把“待确认修订”当作必须继续开发的授权 |
| 文件快照及验证过期记录 | 复用；把必要的核对提前到作判断之前 |
| 提醒去重、压缩后的补回、现有事件流 | 扩展现有入口，不另起一个庞大的提醒系统 |
| 重复失败保护、权限、预算、上下文压缩 | 继续由现有模块负责，避免两套机制重复干预 |
| 离线回归、独立验收和真实模型评测设施 | 复用评测材料与记录方式，补上此次改动的对照条件 |

这些判断分别对应 [Hook 管理器](../codeagent/hooks/manager.py)、[CVM 接入](../codeagent/cvm/integration.py)、[现有防循环](../codeagent/hooks/loop_guard.py)、[提醒追加](../codeagent/agent.py)、[评测任务](../evals/context_journey/cases.py)。

当前最具体的不足有三处。首先，[检查识别](../codeagent/cvm/verification.py) 只支持简单 unittest/pytest 命令；npm、构建、自定义测试脚本还不能直接识别。其次，[文件范围绑定](../codeagent/cvm/evidence.py) 需要明确的输入范围，没有范围就只能说“这次命令的结果”，不能证明当前改动已验证。最后，[结束核对](../codeagent/cvm/integration.py) 主要在本次运行结束时发生，对下一次模型请求的提醒来说太晚。

不要再把识别不了的命令说成“没做验证”，也不要因为命令退出码是零就说“功能通过”。构建通过、类型检查通过、测试通过应分开显示。

**第一步 做出一个看得见的验证监督功能**

做完后，希望用户看到的是这样的过程：

> Agent 修改了文件并跑测试，通过。随后又修改了相关文件。工作台显示“之前的测试结果已过期”，下一次模型请求里收到一次具体提醒。模型重新验证后，状态更新，提醒停止。

一次交付把状态、提醒和可见记录接起来，不把它们拆成多个只做基础设施的阶段。

范围先限于普通单 Agent 的代码修改任务，验证器先使用已有的 unittest/pytest 支持。为测试项目和支持的项目提供一次性、可检查的验证配置，写清命令、工作目录、所检查的输入范围；从可信项目配置或宿主代码注册，不再要求用户每条消息写“验证配置”JSON。配置只描述检查，执行仍走现有工具和权限。通用项目没有可靠配置时，保留未知状态。

程序只维护容易解释的工作状态：

| 状态显示 | 实际含义 |
| --- | --- |
| 尚无当前改动的有效验证记录 | 目前没有足够记录；不猜模型是否做过外部检查 |
| 检查失败 | 指定检查实际失败，附命令和结果引用 |
| 检查受阻或未完成 | 权限、依赖、超时或运行中，不能当成功 |
| 旧结果已过期 | 检查后相关输入又变了 |
| 指定检查通过 | 只针对这项检查及已知输入范围；不等于全部功能正确 |
| 范围或结果未知 | 信息不足，不强行换成通过或失败 |

新增的验证规则只针对两类明确遗漏：改动缺少当前有效的检查，或已有可识别失败仍未处理。它依据以上状态给出具体建议，不计算“信心分数”，不再请另一个模型评分。正常的“编辑后马上测试”应留出执行机会；尚无明确遗漏时保持安静。

同一条事实只提醒一次；新代码版本或新的检查结果才允许重新判断。第一版每次请求最多放一条验证建议，设短长度上限。提醒经已有 `CollectRuntimeReminders` 入口统一投递，不让各 Hook 随意插消息。程序准备发送的提醒，只有进入最终模型请求才记为“已送达”；被压缩、裁剪、取消的候选不能冒充已送达。

新建议规则使用独立开关，便于只比较“是否提醒”这一件事。证据观察可以继续复用 contract 的 shadow 模式取得任务身份；不必为了记录证据启用旧目标的 active 提示投影。原有配置继续兼容，已经启用的功能不偷偷改默认值。

在提醒前、模型准备结束前核对相关文件是否变化，复用现有快照；不对每个 token 或每个读取动作扫描整个仓库。普通工具改动可先标记需要核对，外部编辑在判断边界再检查。必须区分这次任务的变化和启动前已有的用户修改。

工作台复用现有事件列表和详情区，至少让用户看到：触发原因、涉及的检查、提醒是否发送、后续是否运行检查以及结果。原始事实继续用原账本，必要的提醒状态放现有检查点，不新增一组平行数据库表。

遇到“不要运行测试”“暂停开发，只做交接”、只读问答、纯文档修改时，监督不能擅自扩大任务。无法确认当前是否仍允许继续开发时，只展示事实，不要求执行动作。现有任务契约仍有自然语言识别限制，不能把旧目标或 pending 修订当成继续行动的授权。

第一步不自动增加模型轮次、不主动执行检查命令。模型直接结束时，可以留下“尚未验证”的状态给用户；结束前强制补做留到最后的可选步骤。

**第一步怎么验收**

用临时小项目走真实 Agent 循环和真实工具，模型部分先用固定响应，核对下列场景：

1. 改文件、检查通过，再修改相关输入：下一次请求前状态已过期，提醒带正确检查引用。
2. 检查失败、修复、再次通过：失败提醒解除；另一个无关检查通过不能清掉这次失败。
3. 没有修改、只做问答，或已经立即完成所需验证：没有多余提醒。
4. 未知命令、零测试、全部跳过、输出不完整、超时、取消、进程未结束：不显示“验证通过”。
5. 新任务、跨会话恢复、压缩、并行和重试：不串用别的任务证据，不重复投递同一事实。
6. 用户禁止测试或只要交接：没有自动调用、续轮或反复催促。
7. 开关关闭：原有请求、权限和停止行为保持基线；原 CVM、Hook 和执行回归继续通过。

交付时必须能演示“改动 → 旧验证过期 → 一次具体提醒 → 新检查 → 状态更新”。只多几个字段或只增加日志，不算这一步完成。这证明接线正确，还没有证明真实模型更会完成任务。

**第二步 比较到底有没有帮助**

第一步的代码先在小范围使用，接下来用同一模型、同一任务起点和相同权限、预算做开关对照。两组都保留相同的事实采集，唯一差别是是否向模型投递新提醒。保持现有任务契约、摘要配置等不变，避免把别的改动算成提醒的效果。

复用 `evals/context_journey` 的任务和独立验收方式，包括需求变更、已完成工作不重复、未测试如实报告、暂停只交接；再增加测试后重改、实际测试失败后修复、正常一次验证完成、检查受阻等情形。每组从独立工作区开始，交替先后顺序，不共享历史和提醒状态。

第一批建议选 8 个小场景，每个场景每组重复 3 次，共 48 次运行。这只是用于筛选的起点，不是统计显著性的保证；开始真实模型运行前明确模型和费用上限，超时与失败也保留结果，不只展示成功样本。

现有 `run_project_tests` 是受控测试工具，目前不会被仅识别 Bash 的证据适配器自动识别。复用它时要从可信工具实现接入结构化检查结果和源码版本，不凭工具名或模型输出猜成功。Bash 路径另外在临时项目验证。C01 原始评测不开放 shell，不能直接当作 Bash 验证监督的证明。

每次运行同时看三类结果：

- 任务结果：独立检查是否通过，有没有越权修改，有没有把未验证说成通过。
- 行为变化：提醒真的送达后有没有开始相关检查，检查是否完成、是否通过、是否仍对应当前代码。这四项分开计数。
- 代价：多用了多少模型轮次、时间和 token，有没有重复提醒或把简单任务拖长。

Agent 自己运行的检查作为过程证据；最终功能是否正确，使用它不能修改的独立验收。不用 CVM 自己的“已验证”字段给 CVM 自己评分。主观的自然语言汇报单独人工复核，不强行用几个关键词代替真伪判断。

进入下一步的条件是：目标问题在配对样本中减少，没有出现新增的权限/暂停违约，正常任务没有明显变差。建议先约定额外模型轮次中位数不超过 1；时间/token 增幅超过 10% 时逐项复核是否值得。这些是工程取舍线，不是来自 Tianshu 的科学定律。看不出收益就保持可选或关闭；误报明显就修窄规则，不靠多加提醒补救。

测试通过只能证明实现可运行；这一步决定功能是否值得默认启用。暂不移植 Tianshu 的在线随机扣留、自动降频、复杂加权反馈，先用容易复核的开关比较。

**第三步 有收益后覆盖日常项目**

当小范围规则确实有用，再扩大检查适配范围。以你的项目为例，优先补 Python 自定义验收脚本，以及 `web/package.json` 已有的 `test`、`typecheck`、`build`。复用同一套验证规则和状态，不为每个命令复制一个 Hook。

项目配置只负责告诉程序“这条命令是什么检查、在哪里运行、关联哪些输入”。测试脚本需要真实测试汇总，构建和类型检查按各自语义处理。脚本内容或检查配置改变后，旧结果也要失效。不了解的命令仍显示未知，不能把名字里含 test 当成充分依据。

验收覆盖前端测试通过但类型检查失败、只检查一个模块却改了两个模块、Python 检查通过后改了配置、开发服务器退出异常、脚本零测试等情况。展示具体缺口，不显示无法解释的百分比，也不因为一个检查通过就把整个任务标绿。新增适配器分别复做开关比较。

这一阶段仍不另做重复失败检测或上下文压力评分：现有 LoopGuard 和 ContextManager 继续负责。若真实轨迹后来显示“所有工具都成功，但一直重复读同样内容”，再单独立项研究这类现有保护没有覆盖的停滞，不预先搬来全套 Sensorium。

**可选的第四步 收尾前最多补一次明确验证**

只有在前面的比较证明提醒有用，但仍有清楚的“未完成验证就收尾”问题时，才增加控制型 Hook。

触发条件要窄：这是当前允许执行的代码修改任务；存在明确要求且未完成的检查；程序知道检查范围和下一步动作；尚有预算；用户没有暂停或禁止检查。缺范围、未知命令、权限受阻、任务含糊时，不强制继续。

在自然结束的控制判断处先刷新证据，最多多给一次模型机会。若不能执行或仍未通过，允许结束并向用户显示未验证/受阻状态；不为了“全绿”一直循环。一次机会的额度按本次逻辑执行保存，恢复检查点不能重置成无限机会。用户取消、权限决定、预算终止优先，CVM 不得覆盖。

现有 `Stop` 调用把返回的真值当作消息后续轮，并没有完整处理带类型的 `HookDecision`。实施时必须把这个调用点的返回含义、续轮额度和消息投影接清楚，不能只注册一个控制 Hook 就认定结束保护完成。

验收检查：只续一次；已满足不续；用户禁止不续；取消立即生效；失败后诚实结束；恢复不重置额度；Todo 的停止检查和 CVM 不互相触发无限续轮。必须使用完整生产 Hook 组合测试，不能只测单个函数。

**代码保持清楚的做法**

沿用现有分工：`evidence.py` 保存事实；`verification.py` 识别检查；`integration.py` 接生命周期；`HookManager` 调用观察者或控制者。可以增加一个很小的状态归纳模块和一个验证建议模块，但不复制第二份目标、账本或主循环。

规则读取状态后只产生“建议及原因”，统一入口负责把建议写进模型请求；观察者负责记录后续动作；控制者仅负责那一次有界续轮。`agent.py` 保留调用点和原有请求构建，规则分支留在 CVM 模块。证据采集、权限和上下文管理继续按各自边界运行。

本方案不预排全套认知分数、星域/勇气机制、自动学习、多个模型互相审查或完整高风险断言库，也不强制所有修改先写测试。任务目标解析保持现有原文与来源，不继续增加需要用户记忆的特殊聊天语法；若以后目标变更确实频繁出错，再针对真实例子单独改进。

建议从第一步开始。它完成后，用户应当看得见一次真实检查如何影响提醒；第二步决定有没有必要继续扩大。前两步没有收益时，后两步不自动开工。
