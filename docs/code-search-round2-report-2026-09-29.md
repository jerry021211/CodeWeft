# 代码检索第二轮：退步原因、最小修正与全部验证结果

日期：2026-09-29。第一轮版本记为 B1，本轮最小修正版记为 B2；A 是加入 search_code 之前的程序。所有 A/B 数字使用第一轮已统一的装饰器边界和最终标签，不再修改评分规则。

**结论：第一轮首条命中退步主要发生在 Agent 最终引用阶段，并非新工具候选排序造成。本轮修正了一个可复现的查询改写条件错误，并补充引用核对说明。完整 20 题的首条命中恢复到 15/16，但重复验证仍出现新的引用错误，因此尚未证明质量稳定提高。**

## 1. 指标究竟衡量什么

| 指标 | 评分对象与条件 | 原有正式集分母 |
| --- | --- | --- |
| Hit@1，首条严格命中 | Agent **最终答案数组第 1 项**：路径、精确符号、连续原文、片段首行匹配，引用≤20行，含所问行为证据 | 16 道有答案题 |
| Hit@5，前五严格命中 | Agent **最终答案前 5 项至少一项**满足上述条件；无效项占位置，不先过滤 | 同样为 16 |
| 跨文件找全 | 最终前五覆盖所有必需证据组 | 4 道跨文件题 |
| 无答案误报/正确拒答 | 另外检查没有内置实现的题；不混入 Hit 分母 | 4 道无答案题 |

有答案题失败、超时、漏答仍进入分母。四道关注/对照题各重复两次，分母是 **8 次有答案任务**；四道新题只有三道有答案，因此 Hit 分母是 **3**，不是4。

Hit@5 不代表“五条全对”。跨文件题找到任一环节即可贡献一次 Hit，是否找全另算。MRR 是首条有效最终名次倒数的平均；nDCG 衡量前五中有效相关文档的次序，相关替代实现也参与理想排序。详细公式和逐题判定见 [轨迹审计](../eval-results/code-search-round2/audit/analysis.md)。

**search_code 候选数组与最终答案数组是两个排名。** Agent 可以继续 grep/read，丢弃工具候选、重新排序或加入其他函数。第一轮 N08 的工具目标排第2，最终答案排第1；本轮新题 H02 也出现工具第2、最终第1。两者不能混算。

观察到的近因是确定的：N02超行数、N04首行绑定错。为什么模型在某一次选择了不同引用长度，日志不能证明；新增工具schema可能改变生成策略，但不能据此断言它稳定引发退步。

## 3. 为什么只有5/20题使用新工具

逐条检查，**20/20题、100/100个主模型请求都正确暴露了search_code定义**。另1次是工具内部关键词改写请求，不应携带工具。没有漏注册、工具名错误或中途消失的证据。现有说明已介绍中文需求、函数定位、关键词与源码片段；没有足够证据将未使用归因为“说明不清”。

| 分类 | 实际证据 | 判断 |
| --- | --- | --- |
| 旧工具已能完成 | 15道未用题中，12道有答案题均已找到正确函数；另3道正确拒答 | 不必为了使用率强制调用。N02/N04是最终引用问题 |
| 仍可能有效率空间 | N06用了13次工具，C04用了10次 | 旧流程能完成，不等于已经最省；现有证据还不能证明加入search_code一定更省 |
| 明确有用 | E01、E03工具目标排1，N08排2，最终三题均首条有效 | 有函数定位价值 |
| 调用后没提供核心实现 | C01前五不含所需实现，Agent随后用旧工具找到 | 不能用最终答对反推该次搜索有帮助 |
| 不能据此证明不存在 | Z03搜索返回测试/无关函数，随后继续检查后拒答 | 返回候选不是完整的不存在证明 |

B1实际使用工具的4道有答案题里，工具目标首位2/4、前五3/4；Agent最终首位4/4。这组诊断只针对4次实际调用，不能充当正式16题命中率。

本轮完整B2自然使用新工具 **7/20题、共8次**，没有强制调用。使用率变化只是观察值，不是优化成功标准。

## 4. 只做了两个产品修改

### 查询改写触发条件

旧逻辑把任意长度至少3的英文词当作代码定位线索。例如中文行为需求结尾加普通单词error，就会跳过改写。第一轮C01确实走了这条分支；独立的widget小例子也复现了问题，未使用正式题路径或答案映射。

新逻辑识别明确代码形态：snake_case、camelCase、限定名、路径、带编号标识符或明确引用的字面量；普通英文单词不再自动压制中文需求扩展。真实精确符号命中、Agent已提供keywords以及预算约束的豁免保留。

变更：[service.py](../codeagent/code_search/service.py)。未调整BM25/RRF权重、默认候选数、片段挑选或索引架构。

### 最终引用核对说明

在read_file工具说明里明确：复制连续源码，片段首行使用实际显示行号，不混用函数定义行/搜索重点行；按用户要求核对末行−首行+1，超限选更短连续片段，不拼接。

变更：[read.py](../codeagent/tools/read.py)。读取行为、接口和返回格式不变；不增加自动纠错或额外模型调用，不改评测提示来替答案放宽条件。**它是行为提醒，后续结果证明它不能保证模型每次遵守。**

本轮产品程序只改上述两处，并增加通用形态/改写分支的测试。已有修改保持，评分器与第一轮最终标签的内容哈希未变；正式测试所用产品快照与当前产品一致。冻结标识记录于 `eval-results/code-search-round2/fixed-engine.json`。

## 5. 修正前后重复验证：不只选通过的一次

在相同模型、接口、预算、题目和冻结源码下，B1旧程序与B2修正版各对N02、N04、E01、N08重复两次。每次新进程、独立冷索引。没有把原先最好的一轮混入这次重复均值。

| N02退步题 | 0 / 1 | 1 / 1 | 1 / 1 | 1 / 1 |

B1的N02重复1再次超过20行，证明错误可复现，但并非必现。B1的N04两次已经通过，不能把后来通过全部算作修正收益。

**重复结果没有证明稳定质量提升：首条持平，前五反而少一次。** N02两次都通过只是局部迹象。完整 [重复对比](../eval-results/code-search-round2/repeat-comparison/report.md) 保留全部16次任务及费用。

## 7. 直接调用区分工具本体与Agent行为

原始5次工具调用的25条候选，源码哈希、逐字正文、起止行、20行上限全部通过。源码真实不等于证据充分，例如长函数默认片段可能没有覆盖所问分支；本轮没有基于这一潜在问题调整片段算法。

另单独重放第一轮C01的**同一条原始工具输入**。B2成功触发一次改写，但默认前五仍未包含ToolRegistry.execute。保存实际模型改写词后离线逐路追踪发现：

1. 目标正常建入索引；原始中文加error这一路的未截断FTS排名为92，没进前20。
2. 三路真实改写中，目标分别排11、未进前20（未截断为45）、4。
3. 目标已经进入候选池，但RRF融合后排10，默认只返回前5，因此仍未提供给Agent。

**这时才有直接证据说明剩余问题在融合排名/前五截断，而不是索引漏收或所有路都未召回。** 不能仅凭第一轮整体首条下降得到同样结论。也不能把这次直接探测与完整B2中Agent自带keywords的另一条C01查询混为一谈。

本轮门控修正改善了该次查询的候选池覆盖，没有改善其返回前五。保留这个未解决问题，不基于单个已见正式题继续调权重、扩大默认返回量或加新架构。原始模型改写、各路前20与融合前40的记录见 [阶段定位](../eval-results/code-search-round2/tool-audit/direct-replay-stages.json) 和 [直接重放](../eval-results/code-search-round2/direct-recorded-query/result.json)。
