# 工具审批模式设计

日期：2026-10-29。状态：首版已实现，验证记录见文末。浏览器第二、三期继续暂缓。

## 问题与现有调用链

`codeagent/permissions/policy.py` 的 `PermissionPolicy.check()` 对所有 `mcp__` 工具无条件请求审批，未区分工具用途和参数。这是浏览器快照、导航等操作也反复请求人工确认的直接原因。

现有入口为 `CreateRunRequest → RunScheduler → WebAgentFactory → PermissionPolicy → PreToolUse`，需要人工决定时由 `WaitingPermissionBroker` 等待，scheduler 保存审批记录并通知前端。应保留这条链路，在策略层决定何时允许、询问或拒绝，不靠提示词让模型自行绕过审批。

服务配置的信任由 `McpTrustStore` 单独管理；只读、规划和受管理工作区还有独立检查。它们与“是否逐次询问”不是同一个维度。

## 用户界面和三种模式

在输入框工具栏增加独立的审批菜单，和现有 Agent / 只读、先出方案并列。不要替换现有工作方式，否则会把执行能力和审批策略混在一起。

| 模式 | 建议文案 | 行为 |
| --- | --- | --- |
| 请求批准 `ask` | 联网、外部工具和有风险的操作执行前询问 | 常规项目内读写沿用已有许可；联网、MCP 调用、破坏性或不明确的命令进入审批。工作区外访问仍受现有限制。 |
| 自动审批 `auto`，默认 | 常规操作自动执行，有风险或无法判断时询问 | 由宿主规则判断操作类型与参数；已识别的低风险操作放行，高风险和未知操作询问。 |
| 完全访问 `full` | 工具执行不再逐次询问，仍遵守只读及项目限制 | 跳过工具级人工询问；不跳过服务信任、只读、规划、工作区约束、硬拒绝、取消和执行预算。 |

不照搬参考图中“访问电脑上的任何文件”的说明：本项目当前并非一个由审批菜单切换的操作系统沙箱。若以后需要扩展可访问目录，应另做目录授权，不能借本次改动移除所有工作区保护。

选择完全访问时说明其后果，用户明确选择后本会话记住，不再为每个工具重复确认。新会话默认自动审批，不跨会话继承完全访问。

## 判定机制

复用 `PermissionPolicy`，增加一个小型风险分类入口，返回 `allow / ask / deny`、稳定的原因代码与可读说明。策略只消费由宿主提供的工具身份、参数与已验证证据；模型不能通过参数声明“低风险”来获得授权。

处理次序：已有硬限制 → 操作分类 → 审批模式映射 → 必要时进入现有 Broker → 执行前继续校验原有约束。禁止用一个提前返回的 `full → allow` 绕过硬限制。

首版使用确定性规则，不新增独立审批模型、通用策略语言或复杂规则编辑器。使用现有权限模块和工具注册信息，在必要处增加可选的宿主元数据；现有 `ToolDefinition.effect` 是并发调度标记，不能直接当作安全等级。

| 操作 | 自动审批首版处理 |
| --- | --- |
| 项目内读取、搜索、常规文件编辑 | 沿用已有许可，保留路径检查 |
| 可确定的只读命令 | 自动；复用已有命令识别能力，不把任意脚本或复合命令判为只读 |
| 已核实工具适配中的页面快照、等待、标签页列表 | 自动；根据参数区分列表与关闭/创建等不同动作 |
| 已核实的常规导航和搜索 | 在支持的协议、目标和参数范围内自动；不能将所有 URL 都认作安全，异常协议、敏感查询数据和不明确操作询问 |
| 删除、覆盖重要数据、对外提交、上传本地文件、执行任意脚本 | 询问；已有硬拒绝场景仍拒绝 |
| 未知 MCP、复杂命令、证据不足的浏览器交互 | 询问，并说明缺少哪些判断信息 |

“自动审批”只对已覆盖的操作作出判断，不承诺理解所有脚本和网页的真实影响。例如 `python script.py`、测试命令和构建命令可能执行项目代码，不能仅凭名字保证无风险；未覆盖的命令沿用询问流程。

MCP 适配应关联实际服务配置、实现和版本，不依赖可随意修改的服务别名，也不只检查公开工具名前缀。远端工具的自述和只读标记至多作为辅助信息，不能单独成为放行依据；配置变化后原信任失效，旧适配不能错误沿用。

## 浏览器交互的实际边界

当前 MCP 适配没有向权限策略提供可信的目标页面状态。`browser_click` 既能打开链接，也能付款或发送邮件；`browser_type`、填写表单和按 Enter 也可能触发自动提交。

因此首版先解决确定的重复审批：页面快照、等待、受支持的普通导航等不再逐次询问。点击、填写等在缺少可靠目标证据时仍询问，不能仅凭模型填写的元素描述或按钮文字自动放行。

若要进一步自动判断这些交互，必须补充浏览器适配：从实际页面获得目标、当前地址和页面版本，操作前重新确认目标仍有效，无法解释的事件处理和状态变化按未知处理。它属于审批判定能力的后续扩展，不偷渡为浏览器第二期的侧栏/接管功能，也不在首版承诺实现。

首版不增加“永久批准整个 MCP”或“批准该工具之后的所有参数”。这些授权会将查看列表和删除数据、点击链接和付款混为一谈。需要本轮工具完全免确认时由用户明确选择完全访问，其含义要清楚展示。

## 默认值、持久化和继承

- 新 Web 会话默认 `auto`，保存用户在本会话的选择，刷新和服务重启后可恢复；未发消息时切换也应保存，不能只保存在 React 状态。
- 建议在会话记录增加一个有默认值的 `approval_mode` 字段，并通过既有更新会话接口保存；Run 和用户消息的现有 metadata 记录本轮实际模式，便于追溯和重新生成。
- 运行创建时固化模式。本期运行期间禁用切换；待审批时仍可允许、拒绝或取消。需要换模式则取消后重新发起，不让切换隐式批准已经排队的操作。
- 普通子 Agent、原生协作 worker 和恢复执行继承父运行的固化模式；子任务不得自行升级。只读分析任务始终只读。
- 原生协作的验证命令和旧 Team 验证入口也会单独创建 `PermissionPolicy`，同样继承所属运行模式，不能只改根 Agent 工厂。
- 现有 hooks 的 `permission_snapshot` 纳入审批模式与规则版本，用于区分运行时权限状态；不把已保存的允许结果当作后续参数变化后的授权。
- 未声明模式的旧 CLI/SDK 调用、定时任务和历史运行恢复走明确的兼容路径，先保持旧行为；新 Web 运行由前端显式发送模式。兼容行为只是内部迁移逻辑，不增加第四个界面选项。
- 既有会话下一次新建 Web 运行默认显示自动审批；旧运行的审批记录不改写。定时任务的默认只读和已有配置不因本次界面默认值改变而放宽。
- 分支、重新生成、批准方案后的执行及旧 Team 恢复均需审查模式来源，避免某个入口重建 factory 时回落为错误默认值。必要时让新任务继承源任务记录的模式，但不能复制已失效的审批。

## 小范围实施安排

第一步完成三模式的完整链路：界面与请求、会话持久化、运行快照、统一策略、子任务继承。沿用 Broker、审批卡、现有取消与过期处理。先提供确定的内置规则和与实际服务绑定的 Playwright 低风险适配。

第二步做回归与呈现修复：审批原因与执行错误分别展示。当前 `web/src/lib/processPresentation.ts` 会沿用先前审批的 reason，使 `External MCP tool call` 可能覆盖真实工具错误；修正时应按事件类型区分含义，不删除错误记录，也不改成“失败自动重试”。

预计影响：`permissions`、工具/MCP 元数据接线、Web schemas/api/scheduler/factory、会话存储和前端输入区；继承检查覆盖 `multiagent/adapter.py` 与计划继续执行入口。CLI 和定时任务仅做兼容接线，不顺带增加新界面。

这比只在界面增加三个选项涉及更多文件，因为策略必须传递到真正执行工具的 Agent，且不能在恢复或委派时丢失。修改集中在同一审批数据流，不重构 Agent 主循环，不改提示词，不重建浏览器架构。

## 验收标准

1. 新 Web 会话默认自动审批，刷新后保留用户选择；不同会话不相互影响。
2. 已信任并符合低风险适配条件的浏览器导航、快照、等待连续执行不产生逐步审批弹窗；请求批准模式仍出现审批。
3. 高风险和未知操作在自动模式等待确认；拒绝、过期、取消不会执行操作。完全访问免除工具级询问但不能绕过既有硬限制。
4. 子 Agent 和恢复路径继承正确模式；定时任务和旧客户端不被静默放宽。模式切换不会批准旧请求。
5. 改名或伪装成浏览器的 MCP、失效配置、未知工具、复合命令和过时页面证据不被错误判定为低风险。
6. 工具失败显示真实错误；审批拒绝显示拒绝原因；审批原因不能覆盖执行结果。
7. 自动决策在现有事件流记录模式、原因和结果，敏感参数继续脱敏；不为每次自动允许创建等待审批卡。

回归范围：权限 hooks、只读、规划模式、MCP API/运行时、Web API、原生协作 worker、计划继续执行、取消/过期，以及输入区和 `processPresentation` 的前端测试。
