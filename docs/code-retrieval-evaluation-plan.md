# 按需求找代码：改造前后对比方案

日期：2026-09-28。状态：题集、统计脚本和报告流程已实现，尚未运行真实模型评测。实际命令与计分边界见 [使用说明](code-retrieval-evaluation.md)。

目标是回答：同一个 Agent，在同样的项目、问题和预算下，增加代码检索后，能否更准确地定位相关实现，以及代价如何变化。本方案不测写代码或修复成功率。

## 1. 比较哪两个版本

| 版本 | 能力 |
| --- | --- |
| A：当前基线 | 项目自带、已完成范围过滤和翻页的 glob、grep，以及 read_file |
| B：增加检索 | 保留 A 的能力，额外提供 search_code；其内部查询改写、排名和筛选均属于 B 的成本 |

A 可以自己分析中文问题、转换英文关键词、多次搜索、读取上下文；不能把整句中文直接传给 grep 的失败当作完整 Agent 基线。B 可自行决定使用 search_code 或原有工具，不强制每题调用新工具。

主结论针对普通单 Agent 的只读定位任务。双方都关闭跨题记忆、外部 MCP、Skills、Team、子 Agent及写入工具，保持相同配置；这不等于完整产品所有功能的成绩。

基线不额外提供 rg 或 bash，也不要求安装 rg；v2 已据项目原有检索工具修正配置。已有 C01 评测只覆盖一个读取工具修复题，不能原封不动充当这次基线。

## 2. 小规模开始：20 道正式题，另加 4 道调试题

| 正式题类型 | 数量 | 要测什么 |
| --- | ---: | --- |
| 已知标识符或报错的精确定位 | 4 | 新能力不能让原本容易查到的内容变差 |
| 中文描述行为，不给函数名、路径 | 8 | 能否把需求对应到代码；其中一部分使用与注释不同的表达 |
| 必须找到多处代码才能解释的流程 | 4 | 是否只找到一个相关位置，却漏掉关键环节 |
| 项目当前确实没有对应实现 | 4 | 会不会硬找一个不相关函数当答案 |

合计 16 道有答案题、4 道无答案题。正式题覆盖至少 5 个模块；若覆盖前端，单列语言分组，不能将只测 Python 的结论推广到 TypeScript。

另外 4 道调试题用于调整输出格式、预算、代码切片和检索参数，不计成绩。已经在本次对话反复讨论的“取消等待回答”和已有 C01 的 read_file offset 题，只适合用作调试示例，不纳入正式成绩。

正式题和评分规则在 A 测试前冻结。开发期间只用调试题调整方案；同一功能的近义改写不要跨调试集和正式集分配。正式题不是每次迭代都拿来调参的题库。

无答案题必须先检查实现确认，不能仅凭一次 grep 零匹配判定不存在。题目应范围明确，避免“有没有权限系统”这类可能有多种解释的问题。

## 3. 先规定正确答案，不能让模型自己给自己打分

每题在 Agent 看不到的评分资料中记录：

- 自然语言问题和题目类型。
- 目标源码版本、正确路径、函数/方法全名，或明确的模块级代码块。
- 回答必须覆盖的行为，以及支撑这些行为的原始代码位置。
- 多种等价正确实现位置，避免只认可一个偶然选中的文件名。
- 容易混淆但不负责该行为的位置。

跨文件题使用“必需证据组”。例如一道题需要定位取消信号产生、等待中检查、状态清理三个环节，每组允许一个或多个等价正确位置。找到三个环节才算找全，找到同一环节的三个函数不能算找全。

预期位置通过实际代码核对；模型可以帮助整理，但不作为唯一裁判。若评分后发现遗漏了合法答案，保存评分规则新版本并重评双方原始结果，不能只修改某一方的成绩。

示例仅用于说明标注方法：WebUserQuestions.ask 中的取消检查、等待以及 finally 清理，可以支撑“等待用户回答时取消如何退出和清理”的说明；若题目还要求取消信号来源，就需要加入其它文件的证据。这些是不同题目范围。

## 4. 双方提交同一种答案

每题要求按相关程度返回最多 5 个代码位置，并附一句与问题直接相关的说明和简短原文证据；找不到时明确返回 not_found，无法完成调查时返回 insufficient_evidence。

建议结构：status，以及按顺序排列的 results。每项包含 path、symbol、start_line、end_line、reason、evidence。

评分规则：

1. 路径和符号必须确实存在于目标快照中，引用必须支持所声称的行为；只返回整个文件名或大类名，不算准确定位到函数。
2. 允许合理的模块级配置、路由注册等非函数位置，但事先标注它们的范围。
3. 只评分前 5 项；同一符号重复出现仍占位置，但不增加命中或覆盖次数。其中无关结果在返回噪声中计数。
4. 证据应为必要的少量代码行；不能粘贴整个仓库或巨大文件获得命中。调试阶段确定输出上限并冻结。
5. 最终答案是主评分对象。工具曾经返回过正确函数、但 Agent 最后选错，仍算最终定位失败；工具日志另用于诊断。
6. 缺失答案、超时、超预算属于未完成，不从成绩分母中删除。无答案题中的未完成也不能算正确拒答。

可以自动核对路径、符号、引用和预先标注的证据组，再对有歧义的位置做一次人工复核；复核时尽量隐藏 A/B 标签。无需搭建多模型评审系统。

## 5. 主报告看什么数字

| 指标 | 计算方法 | 含义 |
| --- | --- | --- |
| 首选命中率 Hit@1 | 第一项为有效正确位置的有答案题数 / 16 | 最先推荐的代码准不准 |
| 前五命中率 Hit@5 | 前 5 项至少有一处有效正确位置的有答案题数 / 16 | 是否能把正确代码放进小候选列表 |
| 跨文件找全率 Complete@5 | 前 5 项覆盖全部必需证据组的跨文件题数 / 4 | 是否找到完整的关键流程 |
| 无答案误报率 | 声称找到了对应实现的无答案题数 / 4 | 没有实现时是否硬凑答案；越低越好 |
| 每题模型用量 | 输入、输出、缓存读取和缓存写入 token 分列；报告总量和中位数 | 提升是否伴随更大模型消耗 |
| 每题耗时 | 从接收问题到最终回答/停止；报告中位数及超时数 | 实际定位是否更快 |

前五命中率是主要的“有没有找到”指标；跨文件找全率防止只找到一角就宣称成功。首选命中率和无答案误报率是准确性约束，不能只挑最漂亮的一列报告。

同一批日志可低成本补充：

- 跨文件证据覆盖率：每题命中的必需证据组数 / 全部必需组数，再按题平均；用来区分完全漏掉与只差一步。
- 返回噪声比例：有答案题中，不相关或不存在的位置数 / 返回位置总数；没有任何返回时不记为零噪声成功，命中率会为零。
- 完成率、工具使用次数、实际模型调用次数、新工具使用次数。
- 单题 A/B 对照表：题目、是否命中、是否找全、用量、耗时、失败原因。

错误题保留其实际耗时和用量，不能只对成功题报速度。若比较“完成同样任务节省多少”，另外使用 A/B 都成功的同一批题，并标明样本数。

无答案题还应列出正确 not_found、误报和未完成的原始数量，避免工具直接失败却得到看似很好的低误报率。

## 6. 怎样保证对比公平

**冻结的是两样东西：待搜索的项目，以及负责搜索它的 Agent。**

待搜索项目使用同一份只读快照，A/B 都搜它。开发 B 时增加的新工具代码、评测题和报告不能进入这份目标源码，否则前后题目答案和搜索范围会一起变化。

当前工作区有未提交和未跟踪文件，所以不能只记一个 Git commit。需要保存文件清单和内容哈希，包含属于项目的未提交源码；凭据、运行记录、历史评测产物及评测答案不进入搜索语料。

保留既有忽略规则和 Git 文件枚举语义。已有研究文档可能直接包含“问题→答案位置”，应从双方的正式搜索语料中排除这类评测/分析资料，而非只在 B 中排除。正常产品文档是否纳入，应在冻结清单时统一决定。

同时冻结 A 的执行框架源码和配置，使之后仍能复跑当前基线；B 使用新框架，但搜索同一份旧的目标项目。框架导入与待搜索目录分开，避免加载到错误版本。

其它固定条件：

- 相同主模型、供应商、可固定的模型版本、温度/推理设置、上下文和恢复策略。
- 相同问题文本、答案格式和提示规则；差别仅是 B 多了检索工具及其必要描述。
- 每题新会话；题间不共享记忆、搜索答案或任务状态，不带入本次设计对话。
- 相同机器与并发度，初次建议串行；记录实际模型响应中的版本及运行时间。
- 相同总预算。初始建议每题最多 120 秒、12 次生成模型调用、24 次工具调用；4 道调试题确定这些值是否合理后，在正式 A 运行前冻结。
- B 工具内部用于改写查询、筛选或重排的生成模型调用也计入 12 次限额和总用量，不给隐藏调用免费额度。查询 embedding 单独记录调用及费用。
- 若相隔较长时间或供应商模型版本变动，最终应复跑保存的 A，并与 B 交错执行，不能把供应商升级当作代码检索收益。

## 7. 搜索索引的成本怎样算

将索引准备与日常查询分开记录：

1. 首次构建索引的时间、模型用量、磁盘占用。
2. 索引已准备好时，每道题的查询时间和全部模型用量；这是主要质量对比的运行状态。
3. 必要时用一个文件改动检查更新成本；这是索引工程检查，不混入固定源码的质量题。

不要只报“热查询很快”，却漏掉首次建设成本。也不要把每道题都重新建索引的时间，当作正常使用成本。

输入输出、缓存读写、查询改写、重排和 embedding 分别记账；不同模型的 token 不能直接当成同价。复用现有 provider usage 归一化和 call_id 去重。没有完整 usage 或可核实单价时，费用记未知，不记零。

## 8. 现在测、改完再测的实际顺序

1. 选 4 道调试题和 20 道正式题，核对答案；冻结正式题、评分规则和目标源码清单。
2. 用 4 道调试题检查输出和预算，冻结运行配置，保存当前 A 框架快照；正式题不用于调参。
3. 运行 A：20 道题各一次，保存原始回答、工具轨迹、实际请求/响应和用量。20 次任务可能对应远多于 20 次模型调用。
4. 实现 B。用调试题开发，保留现有工具，不修改正式目标项目及题目。
5. 用同一配置运行 B：同样 20 道题各一次，生成逐题配对报告。
6. 若只差一两道题、波动明显，或需要对外报告，再给双方完整重跑一轮，不能只重跑 B 的失败题。重复结果逐题保留，不取“最好一次”。

初轮共 40 次正式 Agent 任务，另有少量调试任务。它用于判断改造方向和发现失败模式。只有 16 道有答案题、4 道无答案题，百分比波动较大；必须同时展示原始分子/分母。重复运行只能帮助观察稳定性，不能把同一道题的多次运行当作更多独立问题。

需要量化不确定性时，按题进行配对统计；同题多次运行先聚合，不能按单次试验伪造更大的样本量。初轮不要求复杂统计平台，也不声称跨项目普遍提升。

## 9. 报告样式与判读

以下数字仅演示，**不是实测，也不是预期承诺**：

| 指标 | A | B | 变化 |
| --- | --- | --- | --- |
| 首选命中 | 7/16 = 43.75% | 11/16 = 68.75% | +25 个百分点 |
| 前五命中 | 10/16 = 62.5% | 14/16 = 87.5% | +25 个百分点 |
| 跨文件找全 | 1/4 = 25% | 3/4 = 75% | +50 个百分点 |
| 无答案误报 | 2/4 = 50% | 1/4 = 25% | -25 个百分点 |
| 每题输入 token 中位数 | 12,000 | 9,000 | 减少 25%，另列输出及缓存 |
| 每题耗时中位数 | 30 秒 | 22 秒 | 减少约 26.7% |

“62.5% 到 87.5%”是提高 25 个百分点；相对提高 40%。应优先报告前一种写法及原始题数，避免混淆。

再列出有答案题的四种配对结果：双方都对、A 错 B 对、A 对 B 错、双方都错。若 B 多做对 5 题、同时退步 1 题，净增是 4 题，不能只展示改善的 5 题。

不提前承诺某个提升比例。判断时先看中文需求和跨文件题是否改善，再看精确题是否退步、无答案题是否更爱乱报，最后评估耗时与成本的交换。准确性持平但花费更低，结论应写效率改善；准确性更高但成本更高，明确报告代价。

## 10. 如何复用已有工程

当前 evals 已有源码快照、独立工作区、公开请求/响应记录、事件、SHA-256 清单和 usage 汇总机制。可复用 evals/evidence.py、evals/metrics.py 及现有客户端记录方式。

需要新增的是小型只读定位 profile、题目/答案资料、结果格式核对和配对报告，不需要新增评测平台、Web 面板或大规模修复测试。现有 C01 的固定答案客户端只能测接线，不能测检索质量。

主报告比较的是“Agent 最终定位能力”。B 建成后，可从同一次工具日志额外看 search_code 返回的候选是否包含正确函数，用来区分检索没召回、排名没选好、Agent 没用好；这些工具内指标不能冒充 A/B 最终成绩，也无需另起一批模型测试。

参考：RepoQA 的 Search Needle Function 使用不透露函数名的自然语言描述来定位函数，可借鉴题目写法；其原任务是长上下文理解，本方案是自定义工具检索评测，不能直接对照原榜单。[RepoQA](https://github.com/evalplus/repoqa)

CodeRAG-Bench 分别测量检索和最终生成，指出找到有用上下文与有效利用它是两件事；本轮据此区分检索工具候选和 Agent 最终定位，不据定位成绩推断修复成功率。[论文](https://aclanthology.org/2025.findings-naacl.176/)
