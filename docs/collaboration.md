# 多 Agent 协作

[文档导航](README.md) · [规划模式](plan-mode.md) · [项目架构](architecture.md)

CodeWeft 的原生协作允许主 Agent 把明确的子任务交给成员，按依赖与文件冲突安排执行，并汇总报告和验证结果。你可以直接描述任务及约束，由主 Agent 选择是否委派；简单任务仍可由一个 Agent 完成。

上图为一次本地计划执行的界面记录：基础库存任务 A 连接订单 B 和报表 C，最后汇入集成验收 D。界面分别显示任务阶段、检查数量和交付状态；连线表达依赖关系，不能单凭布局判断实际并行。点击图片可查看原图。

## 可用范围

原生协作接入**新建的 Web 普通会话**，无需选择旧 Team 模式。已有会话按检查点保留工具版本；想使用新入口时请新建会话。

CLI 和 Python SDK 的普通运行时仍使用原有 `subagent` 机制：默认继承权限、前台串行执行，显式 `access="read_only"` 的子任务才可并行或后台运行。整个会话启用只读保护时禁止委派。详见 [普通 Agent 并行](parallel-execution.md)，它与本页的原生委派入口不同。

例如，在 Web 中提出：

> 检查登录流程和相关测试，拆分互不依赖的调查任务。先给我修改方案，说明涉及的文件和验证命令。

需要先审批方案时，使用 [规划模式](plan-mode.md)。规划期间可定义任务、委派只读调查，修改和命令检查等待批准后的执行阶段。

## 三种执行方式

| 方式 | 适合什么任务 | 文件在哪里修改 |
| --- | --- | --- |
| `delegate_task` | 一个边界明确的已有 Task | 当前项目目录；不要求 Git |
| `delegate_batch` | 1–5 个已有 Task 的小批次调查或实施 | 当前项目目录；按依赖和冲突分波 |
| `execute_plan` | 1–32 个 Task 的依赖计划，需要阶段验证和统一交付 | 有写任务时使用受管理的协作目录，最终检查后回写本地 |

单任务和批量委派直接修改项目，失败或取消**不会自动回滚已发生的修改**。计划路径保存工作目录和检查点；有隔离要求时通过 `execute_plan` 处理，不能把单任务或批量委派描述为已隔离交付。

主 Agent 选择入口，运行时执行确定性约束：前置任务通过后才推进依赖；声明的文件或共享资源冲突不并行；未知写入范围保守串行。默认最多 3 个成员同时运行。共享目录中的写工具和不透明命令串行执行，成员模型调用可以并行。这不是按任务类型自动学习的负载均衡，也不保证每个任务都能加速。

## 任务与验证

任务始终通过 `TaskCreate`、`TaskGet`、`TaskList`、`TaskUpdate` 维护，依赖使用 `blockedBy` / `addBlockedBy`。执行配置存放在任务的 `metadata.execution`，例如：

```json
{
  "execution": {
    "profile": "implement",
    "files": ["src/", "tests/"],
    "checks": [
      {"argv": ["python", "-m", "unittest", "discover", "-s", "tests"], "cwd": "."}
    ],
    "resources": [],
    "isolation": "auto"
  }
}
```

这是一个 Python 项目的示例，文件范围和命令应替换为目标项目实际内容。`files` 是分工和冲突调度线索，不是权限授权或沙箱。角色有 `research`、`implement`、`review`、`verify`；`research` / `review` 只读，不能配置可执行检查。

成员返回报告后，运行时执行该阶段声明的检查，再推进依赖。没有声明检查的任务只表示阶段成果返回，不能据此声称经过测试。计划路径交付代码时必须有可执行验收检查，并再次检查实际将回写的组合结果；仅有成员自己的“完成”答复不够。

前端任务面板显示同一套 Task 的依赖和状态，对话进度显示“单任务委派 / 批量委派 / 计划执行”、成员报告、检查及阻塞原因。执行阶段区分成员返回、检查通过和最终回写，避免把它们都当成完成。

这套协作检查独立于默认关闭的 CVM。CVM 的可选验证建议及适用范围见 [验证指南](cvm-verification-guide.md)。

## 停止与恢复

停止会传递给成员和检查进程；刷新页面或重启服务不会自行恢复执行。继续时复用原 Task、工作目录和检查点，不应重复创建一套任务。

| 工具 | 用途 |
| --- | --- |
| `AgentRunStatus` | 查询当前会话的执行进度、成员报告、检查证据和阻塞原因 |
| `AgentResumeRun` | 显式继续暂停或受阻的执行；可追加已有修正 Task |
| `AgentRecoverRun` | 核对中断后结果未知的操作，通过现有授权流程允许从现场继续 |
| `AgentCloseRun` | 用户放弃时关闭已停止的执行，取消未完成任务并保留文件与历史 |

普通检查失败交回主 Agent：先读证据，再修改未完成任务的要求或检查命令，然后继续。已接受的成果只调整检查配置时可以重验；需要继续改代码时创建修正 Task，通过 `additionalTaskIds` 接回同一次执行。

如果进程中断导致写操作结果未知，必须先核对保留现场，不能盲目重放。部分本地回写中断也保留交付记录，以便恢复，而不是重新执行所有成员。

## 权限和工作区边界

- 成员继续遵守工具权限。任务拆分、`files` 和 `resources` 不会自动扩大权限；成员不能再次委派。
- 单任务/批量与其他会话、编辑器共享当前项目文件；本次执行的写入锁不隔离其他进程。
- 计划写任务从本地未提交状态生成快照，内部用 Git 记录成果。隔离 worktree 按需使用，最终做合并预览、检查和逐文件回写，保留用户 HEAD 与暂存区，不自动推送远程。
- 同期用户修改、冲突或未知进程结果会阻止交付并保留现场，不能用“自动整合”理解为无条件覆盖。
- 生成缓存遵循项目 ignore 规则，源码和文档不能作为排除项跳过交付。
- 普通运行的中断、重试、取消和轮次预算仍适用；检查通过只说明指定命令在对应文件状态下通过，不保证整个任务没有缺陷。
