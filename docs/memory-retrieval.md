**长期记忆改造：从按名称翻前 50 条，变成按任务查找**

本次保留 Markdown 正文，新增 SQLite FTS5 检索索引，默认启用。安装依赖不变，旧记忆无需手动迁移。上下文压缩策略不在本次修改范围内。

**1. 可以把它理解成给记忆书柜加了一份检索目录**

Markdown 文件是书柜里的书，每条记忆的正文仍在原文件中。SQLite 是可重建的检索目录，保存搜索所需的内容、词项和版本信息。Agent 根据当前任务先查目录，再请模型挑选需要阅读的书，最后读取原文件。

以前从按类型和名称排列的目录中取前 50 条。相关记忆排在第 800 条，选择模型看不到。现在从整个库检索，取相关性靠前的最多 50 条；50 是候选数量上限，不是可搜索范围。

```text
用户提出任务
  → 从本轮明确请求构建查询
  → 检查文件是否新增、改动、删除、改名
  → 在完整索引中搜索并排序
  → 给模型看候选标题、描述和正文证据片段
  → 模型选择最多 5 条，也可以一条都不选
  → 重新读取原始 Markdown，核对版本
  → 按预算放入本轮输入
```

**2. 用一个实际例子理解变化**

假设有一条记忆，标题是“项目约定”，正文写着“事件断线后应继续回放，依据序号去重”。你问：“断线后如何回放事件？”

旧手动搜索可能把整句话当成一个词，要求正文中出现这整句话，因此漏掉；旧自动选择还可能因为文件排序靠后，根本不向模型提供这条记忆。

现在中文会生成相邻双字词项，例如“断线”“线后”“回放”“事件”。常见问句词如“如何”被过滤。索引能从词项重合找到该记录；模型会看到匹配位置附近的原文，再判断是否应该使用。

这是一种轻量词法方法，没有安装中文词典或向量模型。相同词项只是候选证据，不代表语义一定正确。因此仍保留模型选择以及“选空”的能力，不把全部匹配结果直接注入。

代码同样有专门处理：`RunScheduler` 同时保留完整标识符和 `run`、`scheduler` 词项；路径保留完整形式并增加组成词。SQLite 实际索引编码后的词项，避免其内置 tokenizer 再把路径符号拆成另一套规则。查询参数化并编码，不将用户输入作为 FTS 操作符执行。

BM25 会综合词项稀有程度、出现频率和文档长度进行排序；标题/文件名、描述、正文权重分别为 5、3、1。分数用于排序，不是“这条记忆正确的概率”。当前权重是初始工程选择，尚未用真实任务集证明最优。

**3. 模型看到的证据更完整，但不会读全部正文**

候选除文件名、标题、类型和描述外，还包含命中的正文片段、来源与更新时间。片段最多约 500 字符，优先取靠近查询词的位置；标题和描述也有长度限制。

模型仍返回 `selected_memories` 文件名数组。系统只接受候选白名单里的精确文件名，拒绝越界路径别名、非候选项和重复项。选中后才读取原文件，应用默认 60,000 字符预算；过长记录整条跳过，再尝试剩余记录。

本轮原始请求由 Agent 显式传递。超过 6,000 字符时，检索查询保留头尾并标注裁剪，不改变主模型收到的原始用户请求。“继续”“按上次那个方式”等简短续问会补充上一条用户请求，最多约 2,000 字符。工具日志、助手回复和此前注入的记忆不被当成用户意图拼回查询。

**4. 索引怎样跟上记忆变化**

索引文件位于原项目专属记忆目录内：

```text
CODEAGENT_DATA_DIR/workspaces/<workspace-id>/memory/
  project-style.md
  testing-rules.md
  MEMORY.md
  .retrieval-v1.sqlite3
```

首次检索会读取当前 Markdown，建立索引。之后每次查询枚举目录并检查修改时间、大小等元数据：新增文件建立条目，变化文件重新索引，删除文件移除条目，改名按删除旧文件和新增文件处理。

默认每 60 秒，在下一次查询时对所有文件做一次内容核对。它用于覆盖仅靠元数据可能漏掉的修改；不是后台线程每分钟自动运行。因此，外部工具如果刻意保持文件大小和时间元数据不变，查询可能在下一次全文核对之前使用旧的检索目录。需要每次核对时可设置 `MEMORY_INDEX_VERIFY_SECONDS=0`，代价是读取开销增加。

候选版本根据记忆内容和元数据摘要生成。模型选择结束后重新读取正文并比较版本：若在选择期间被改动、删除或变成无效文件，本次跳过并写明原因。不会把未经这次选择的替换正文直接注入，也不会静默使用缓存正文作为最终结果。

没有候选时跳过选择模型。普通回合结束也不再重复全库扫描以重建人工目录；保存记忆仍更新 `MEMORY.md`，索引在下一次检索时同步。手动编辑后，人工目录可能要显式重建或等下次保存更新，检索不依赖这个人工目录。

**5. 只读模式和异常处理**

Discuss、Team 的只读约束继续有效。只读检索会将可用索引复制到内存，必要时在内存刷新；没有现成索引时在内存建立，不创建或修改磁盘索引。手动 `search_memory` 也采用这条只读路径。

索引无法访问或损坏时，使用内存检索，并在观测记录中标出降级原因；不会删除原记忆或自动覆盖损坏文件。需要重建损坏索引时，可在停止相关任务后仅删除 `.retrieval-v1.sqlite3`，下一次可写检索会重建。FTS5 不可用时，退回同一分词和字段权重的 Python BM25 实现。降级不保证与 SQLite 的浮点排序完全一致。

索引包含记忆内容的派生副本，应与原记忆采用同样的数据保护方式。它不是不含正文的纯文件名目录。跨进程索引写入通过 SQLite 事务协调；Markdown 的外部编辑仍由文件检查和加载时版本校验处理。

**6. 如何知道记忆为什么没用上**

每次选择结束会发出 `memory.selection.completed` 事件。Web 的原始事件/调试数据可以查看它，本次没有新增专门的记忆管理页面。

| 字段 | 通俗含义 |
|---|---|
| `candidate_ids` | 搜索找到了哪些记忆 |
| `selected_ids` | 模型从候选里选了哪些 |
| `injected_ids` | 最后真正放进输入的有哪些 |
| `skipped` | 哪条因超预算、版本变化、消失或无效选择被跳过 |
| `status` | 无候选、选择为空、解析失败、模型失败、成功注入等 |
| `backend` | 磁盘 SQLite、内存 SQLite、Python 降级或旧策略 |
| `files_read` | 本次索引刷新读了多少份 Markdown，不含选中后的正文加载 |
| `retrieval_ms` / `selection_ms` / `injection_ms` | 搜索、模型筛选、加载注入分别花了多久 |

事件默认记录查询摘要、长度、候选 ID、版本和分数，不写完整查询或记忆正文。例如候选有 3 条、模型选了 2 条、实际注入 1 条，就能进一步看到另一条是否因预算或版本变化被跳过。

**8. 使用与复跑**

重启原来的 CLI/Web 进程后，默认使用新方式，不必迁移 Markdown 或安装额外服务。

```bash
MEMORY_RETRIEVAL_MODE=indexed
MEMORY_INDEX_VERIFY_SECONDS=60
MEMORY_MAX_ITEMS_IN_PROMPT=50
MEMORY_MAX_LOADED_ITEMS=5
MEMORY_SESSION_BUDGET_CHARS=60000
```

需要比较旧自动候选方式时，设置 `MEMORY_RETRIEVAL_MODE=legacy`。该开关只控制自动候选/选择，手动搜索继续使用新词法检索；`MemoryStore.legacy_search` 为离线旧搜索对照保留。

在项目根目录执行：

```powershell
python -B -m unittest discover -s tests -p test_memory_retrieval.py
python -B -m evals.memory_retrieval_benchmark
```

每次基准生成新的结果目录、合成记忆、关键源码副本和校验清单，不修改真实记忆。

本次没有实现向量召回、自动判断规则是否过期、冲突消解或新的自动记忆提取策略。下一轮应先用真实任务检验候选质量和误注入，再决定是否增加这些能力。
